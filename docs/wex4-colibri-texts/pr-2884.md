## 1. What this adds

`wex_decode.c` opens the CUDA helper of the previous PR at run time and sends it the neural records it decodes. Every engine that decodes WNR3 records through `coli_wex_decode_record` (series 2's hooks) then decodes them on the GPU when the helper is there, with the CPU decoder's bytes, and on the CPU when it is not. Only when asked: `COLI_WEX_CUDA_LIB=<path>` names the helper; unset or `0`, nothing is looked for and every record decodes on the CPU, as before. It also exposes the helper's device and batch calls (`coli_wex_cuda_*`) for the engine PRs after it. RAW containers never load anything.

## 2. Why

On 16 WNR3 records of the published DeepSeek V4.1 Flash REAP-192 container (18,800,640 decoded bytes each), read from a SATA SSD and decoded through `coli_wex_decode_record`: 949-1010 ms per record on the CPU (one thread of an i7-7700K, the reference decoder), 5.9-9.4 ms with the helper on an RTX 3070 (29.6 ms in the first pass, which allocates the workspaces), 0 differences; through `coli_wex_cuda_decode_batch_to_host`, 8 records a call, 4.0-4.4 ms per record (section 9). A V4.1 decode step reads tens of such records when they miss; at a second each on the CPU, the published container is not usable without the GPU.

## 4. How it works

```
first coli_wex_register_model, or first neural coli_wex_decode_record     (pthread_once)
  wex_cuda_load       COLI_WEX_CUDA_LIB unset or "0" -> none (nothing searched for); a path -> it
                      Windows LoadLibraryExA (the DLL's directory and the system's for its dependencies), else dlopen
                      wex_cuda_helper_abi() == 1 and wex_cuda_decode_to_host, else "[wex] ... not a CUDA helper of ABI 1"
                      each other export resolved only when its feature bit is set; WNR3 (16) only with the registry (4)
                      "[wex] CUDA helper <path>: ABI 1, features <bits>"
coli_wex_register_model   the CPU registry as before, then wex_cuda_register_model (bit 4); a refusal: CPU for that model
coli_wex_decode_record    WNR2/WNR3, model in the helper (and bit 16 for WNR3) -> wex_cuda_decode_to_host
                            0 -> done (counted); any other status: the helper left the slab as it was ->
                            the CPU decodes the same record (one "[wex] ... decoding it on the CPU" line, once)
                          anything else: the CPU, as before
coli_wex_cuda_decode_to_device / _batch_to_device / _batch_to_host / _host_register
                          1 when the helper or its bit is missing; a batch passes the helper only the records it
                          can take and reports 1 or -1 for the others
```

## 6. Variables

| Variable | Default | Effect |
|---|---|---|
| `COLI_WEX_CUDA_LIB` | unset (no helper) | a path: that helper (`kaira_wex_cuda.dll` / `kaira_wex_cuda.so`). **Unset or `0`: no library is opened or searched for; every record decodes on the CPU, exactly as series 2** |

The loader runs only when a neural record is registered or decoded, so an engine without `COLI_WEX_PATH`, or with a RAW container, never opens a library and prints nothing. Without a helper the decode is series 2's, unchanged. macOS and other systems: no loader, no change.

## 7. Compatibility and risks

- The bytes never depend on the helper: it decodes into private memory and writes the slab only after a clean decode; any other status leaves the slab as it was, and the CPU decodes it. A damaged record is refused by both.
- Only a library the user names in `COLI_WEX_CUDA_LIB` is loaded, inside the engine's process; nothing is searched for, so a stray file beside the executable is never picked up. On Windows its dependencies are searched in its own directory and the system's, not the current directory.
- The helper's VRAM (its pooled workspaces, one per decode in flight: about 36 MiB each on V4.1 records, about 290 MiB with 8 readers) is outside any backend's accounting; with a backend on the same GPU, leave room for it. When there is none, the helper returns 1 and the CPU decodes the record.
- Linux links `-ldl` (also when VK is off) for glibc before 2.34; on newer glibc it is a no-op.
- Wrong helpers: another ABI, missing exports, a feature bit without its export: not used, or that feature not used, with a line.

## 8. How to test

```sh
cd c
make tests/test_wex_cuda_loader && ./tests/test_wex_cuda_loader 2>/dev/null
```

Passing prints:

```
  ok   the helper decodes WNR3 records to host slabs and device buffers with the CPU decoder's bytes; a damaged record refused, its destinations untouched; the device batch reports 1 without feature 8
  ok   with feature 8: a batch to device buffers, each record where it was asked
  ok   a helper without feature 16: WNR3 records decode on the CPU, the device call reports 1
  ok   the helper does not decode (CUDA unavailable): the CPU decodes the record, same bytes
  ok   a host batch whose copy back fails for one record: status 1 for it, the other one written
  ok   a helper of another ABI: not used, every record on the CPU
  ok   COLI_WEX_CUDA_LIB=0: no helper, every record on the CPU
  ok   COLI_WEX_CUDA_LIB names no file: every record on the CPU
  ok   COLI_WEX_CUDA_LIB unset: no helper, every record on the CPU
  ok   COLI_WEX_CUDA_LIB unset and kaira_wex_cuda.dll beside the executable: not looked for, the CPU
test_wex_cuda_loader: ok
```

(`.so` on Linux; on macOS the test prints that it is skipped.) Each case runs in a child process, since the loader runs once per process. With a GPU: `make wex-cuda-helper`, then any series-2 engine run with `COLI_WEX_CUDA_LIB=<path to kaira_wex_cuda>` prints `[wex] CUDA helper ...: ABI 1, features 63` when it opens a WNR3 container.

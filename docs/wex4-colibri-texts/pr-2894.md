## 1. What this adds

- `c/tools/wex_bench.py` (Python 3, standard library only): the measurements #2860 asks helpers for, as stages that each run alone, and a report to paste into #2860:
  - `env`: OS, CPU model and flags (AVX2, AVX-512F, NEON, SVE), cores, RAM, GPUs (`nvidia-smi`, `vulkaninfo`), compilers, and the bus, media and model of the container's drive where the OS tells it;
  - `verify`: `tools/wex4_verify` on the container, with its time, GB/s and root;
  - `decode`: ms per record on N seeded WNR3 records, for the reference decoder, the fast decoder at each stream count (`--lanes`), both with T records at once, and the CUDA helper when `COLI_WEX_CUDA_LIB` (or `--helper`) names it; every arm's bytes compared with the reference's;
  - `io`: read GB/s of N seeded records, uncached and warm, on 1 and T threads;
  - `engine`: one engine, a fixed prompt, greedy, N tokens, one run per arm (shards; container with the fast decoder; container with the reference decoder; container with the CUDA helper): prefill and decode time, tok/s, the token ids (all must match), the container reads, and which decoder took the records;
  - `report`: `wex-bench-report.md` and `.json`, with the commit, the variables set per stage, the container's root and the records used.
- `c/tools/wex_decode_bench.c` (`make -C c tools/wex_decode_bench`): the C part of `decode` and `io`; it includes `wex_decode.c` and `wex_fast_decode.h` as the engines do.
- `COLI_WEX_STATS=1` (a separate commit): one stderr line from `wex_decode.c` at exit, `[wex] stats: helper=H device=D fast=F reference=R failed=X cpu=AVX2`. The engines had no counter output for this (the series' tables came from a one-off build that printed `coli_wex_cuda_decode_count()` and `coli_wex_fast_decode_count()`).
- `docs/wex-bench.md`, a short section in `docs/wex.md`, `docs/ENVIRONMENT.md` (the variable, in the three engines' tables), CHANGELOG.

## 2. Why

Every number in the series comes from one desktop (Windows 10, i7-7700K, RTX 3070) and its WSL2, plus one Apple M4 run of #2888's test on synthetic records (mfethe1, on #2888). What is missing is other hardware: native ARM64 Linux, Apple silicon end to end, `WEX_FAST_LANES` per CPU on real records, the CUDA helper on Linux and on other GPUs, AMD and Intel GPUs, low-RAM machines, two drives (#2860 now lists them). Each PR's section 8 gives its commands, but a helper would have to collect them from ten PRs, build scratch harnesses for the timings, and write down the conditions by hand. This makes it one command and one report, and the same records on every machine (seeded), so reports can be compared.

## 4. How it works

```
wex_bench.py STAGE ... --container FILE [--snap DIR] [--helper LIB] --out DIR
  env      platform / /proc/cpuinfo / sysctl / IsProcessorFeaturePresent, nvidia-smi, vulkaninfo,
           cc --version, nvcc; the drive: Get-Disk + Get-PhysicalDisk (Windows), /sys/dev/block (Linux),
           diskutil info (macOS); a WSL /mnt/c (9p) or a network share: "the drive is not visible"
  verify   tools/wex4_verify FILE 8 (built if missing), timed; COLI_WEX_ROOT=... parsed
  decode   tools/wex_decode_bench decode FILE --records N --seed S --lanes L --threads T
             the N records picked by the seed (a partial Fisher-Yates over the WNR3 expert records), read into memory
             reference, 1 thread: its 64-bit hash of every decoded record is the one every other arm must give
             fast, 1 thread, each stream count: wex_fast_decode_record {1 thread, kernel 1, L streams, fused}
             reference and fast, T records at once (OpenMP, T slabs); the decodes timed, not the copies or hashes
             CUDA helper: coli_wex_decode_record (a warm-up pass, then P passes; the helper's own count must
               grow by every call, or the arm fails), and the host batch of 8 when the helper has it
             best and median of P passes (default 3; the reference 1), ms per record and GB/s decoded
  io       tools/wex_decode_bench io FILE: N seeded records, read whole, one request a record:
             uncached (FILE_FLAG_NO_BUFFERING / O_DIRECT / F_NOCACHE; posix_fadvise DONTNEED where O_DIRECT is refused)
             warm (buffered, the second pass after one that fills the cache); 1 and T threads
  engine   per arm: SNAP, COLI_WEX_STATS=1, and for a container arm COLI_WEX_PATH, COLI_WEX_ROOT (from verify),
           COLI_WEX_FAST_DECODE=1/0, COLI_WEX_CUDA_LIB=<helper>/0; every other COLI_WEX_* removed;
           deepseek_v41 CAP prompt.json (prompt_ids + zero output_ids: the engine prints its own tokens);
           parses "[v41] prefill ... | decode ... tok/s", "[v41_wex] container: ...", "[wex] stats: ..."
  report   the results file -> wex-bench-report.md / .json
every string written or printed goes through one filter: paths -> <repo>, <container dir>, <checkpoint>, <path>;
the user name and host name -> <name>; path-valued variables -> <set>
```

`COLI_WEX_STATS`: `wex_decode.c` counts the reference decodes and the refused records beside the two counts it already had; the first model registered or neural record decoded with the variable set registers one `atexit` line. The same in the three engines, because they all decode through `coli_wex_decode_record`.

## 6. Variables and defaults

| Variable | Default | Effect |
|---|---|---|
| `COLI_WEX_STATS` | unset (off) | `1`: one stderr line at exit, `[wex] stats: helper=H device=D fast=F reference=R failed=X cpu=AVX2`. Unset or `0`: nothing. |

The bench itself reads `COLI_WEX_CUDA_LIB` (or `--helper`) for the helper arms, and passes every other variable through to the engine (so `COLI_VULKAN=1`, `COLI_MODEL_MIRROR`, `COLI_DISK_WEIGHTS` work as usual), except the `COLI_WEX_*` ones, which it sets per arm. Its defaults: 16 records, seed 1, `--lanes 2,4,6,8`, T = the OpenMP team (at most 8), 3 passes (the reference 1), 8 tokens, 8 expert slots for deepseek_v41.

## 7. Compatibility and risks

- Engines: with `COLI_WEX_STATS` unset, two more relaxed atomic adds per decoded record and one `getenv` per decode (beside the one `COLI_WEX_FAST_DECODE` already does), next to a decode of megabytes; the fast-decoder count is unchanged (`test_wex_fast_decode` checks it). With it set, one line at exit; an engine that leaves with `_exit` prints none.
- The bench only reads the container and the checkpoint. It writes only in `--out` (the results, the report, a prompt file and one log per engine arm), and it builds the two tools (or the engine, if missing) with `make -C c`.
- Privacy: the scrubbing is a filter, not a proof; `docs/wex-bench.md` and #2860 ask helpers to read the report before pasting.
- Timings: one run per engine arm, page cache not dropped between arms (as in the series); "uncached" is what the OS gives for unbuffered reads (on a WSL `/mnt/c` it is `posix_fadvise` over 9p, not a cold drive). The decode bench hashes with a 64-bit mixing hash (an identity check between arms, not a digest).
- Engines: `deepseek_v41` was run here; the `qwen38` driver (its `prompt_ids` / `full_ids` reference mode) and `--engine custom` were not (no Qwen3.8 trunk or V4 checkpoint here), and say so in the docs.

## 8. How to test

```sh
cd c && make tests/test_wex_fast_decode tests/test_wex_decode tests/test_dsv41_wex4 tests/test_qwen38_wex4 && cd ..
c/tests/test_wex_fast_decode 2>/dev/null | tail -1           # test_wex_fast_decode: ok (the counts it checks are unchanged)
COLI_WEX_STATS=1 c/tests/test_dsv41_wex4 2>&1 | tail -1      # [wex] stats: helper=0 device=0 fast=123 reference=0 failed=1 cpu=AVX2
make -C c check-env                                          # check-env: 866 variables, registry matches the sources
```

With a container (no model needed):

```sh
python3 c/tools/wex_bench.py all --container v4_flash_experts.nr3.wex --out bench-out
```

prints each stage's table and ends with the report; `decode` ends with `every arm gave the reference's bytes` and exits 0 (1 if any arm differs), and a RAW container's `decode` says `no WNR3 records here (a RAW container): nothing to decode`. With the model:

```sh
make -C c deepseek_v41
python3 c/tools/wex_bench.py engine report --snap DeepSeek-V4.1-Flash-REAP192-MXFP4 \
    --container v4_flash_experts.nr3.wex [--helper c/kaira_wex_cuda.dll] --out bench-out
```

ends with `engine: the same tokens in every arm` (exit 0; 1 if the arms' tokens differ). Each engine run exits 1 itself, because the prompt file holds zeros as the reference output (the engine prints its own tokens, which the bench compares across arms); that is expected.

## 9. What I ran

- Windows 10, i7-7700K, MSYS2 UCRT64 gcc 16.2: `test_wex_fast_decode`, `test_wex_decode`, `test_wex_cuda_loader`, `test_dsv41_wex4`, `test_qwen38_wex4` pass with the stats commit; `COLI_WEX_STATS=1` prints `[wex] stats: helper=0 device=0 fast=12 reference=6 failed=18 cpu=AVX2` for `test_wex_fast_decode` (its 6 reference calls and 18 deliberate refusals) and `fast=123 ... failed=1` for `test_dsv41_wex4`; `make check-env`: 866 variables, registry matches. `tools/wex_decode_bench` builds with no warning.
- Linux, Ubuntu 26.04 under WSL2, gcc 15.2: the same tests pass, again under ASan + UBSan (`-fsanitize=address,undefined -fno-sanitize-recover=all`), and `tools/wex_decode_bench decode` and `io` on 2 real records under ASan + UBSan: no report; `make check-env`: 866.
- **The bench, every stage**, Windows: the published DeepSeek V4.1 REAP-192 WNR3 container (root `f0f78a84...eeb1`) on a Samsung 970 EVO Plus NVMe, the checkpoint on a SATA SSD, the CUDA helper of #2883 on the RTX 3070; and the published Qwen3.8 RAW container (root `db5389f6...c0df`) on a SATA SSD (env, verify, io; decode says it has no WNR3 records). WSL2: the same two containers through `/mnt/c` and `/mnt/h` (9p), CPU stages only (env, verify, decode, io). The reports below are the bench's own output, unedited; their commit line is the branch's head, regenerated after the last commit (the measurements ran on its first two commits; the later changes are the RAW-container message, the report layout and the scrubbing of the word "root").
- **Conditions, read before comparing**: the machine is shared, and from 22:23 UTC another job ran on it (a `make -j6 test-c` of another branch and a container verify on the SATA drive). The Windows env, verify, decode and io stages ran before it (22:01-22:07 UTC). Of the engine arms, `shards` and `container-fast` ran before it; `container-reference` partly and `container-helper` entirely during it, and the WSL2 stages during it too. A decode rerun under that load (not in the report) gave 432-639 ms a record for the fast decoder against 117-161 ms. So the helper arm's 75.0 s here is not comparable with #2889's 35.2 s (no other job then), and the WSL2 decode numbers are low; the token ids and the decode counts are what these runs show.
- What the runs show: the bench gives the same token ids in all four engine arms (`6247 14 9214 14 14817 343 2869 288`, as #2879 and #2889), and the stats line accounts for every record (2,257 of 2,257) on the decoder each arm asked for: the fast CPU decoder, the reference, the helper. The decode stage's tables agree with #2889 (fast 4 streams 7.3x the reference on one thread here, 7.3x there) and on real records 4 streams are the fastest on this CPU (117 ms against 147-161 for 2, 6 and 8), where mfethe1's M4 found 6 on synthetic ones: the per-CPU question the bench is for.
- Not run: macOS and ARM (the bench's `sysctl`, `diskutil`, `F_NOCACHE` and NEON paths); the `qwen38` and `custom` engine drivers (no Qwen3.8 trunk or V4 checkpoint here); the helper on Linux (no CUDA toolkit in this WSL2); the engine under WSL2; a machine without `nvidia-smi` or with `vulkaninfo` for another vendor. Not relied on: colibri's CI.

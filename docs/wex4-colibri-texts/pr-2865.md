## 1. What this adds

`deepseek_v41` can read its backbone's routed experts from a WEX4 container, `COLI_WEX_PATH=<file>`: an expert's six tensors (three FP4 matrices and their scales) come from its one record in the container instead of six places in the shards. The engine's own readers do the reads, into the same windows. `COLI_WEX_ROOT` pins the file and checks each record's SHA-256 at its first read; a record that fails is read from the shards. Unset, nothing changes.

## 2. Why

DeepSeek V4.1 Flash is the model this container was built for. In a downstream fork of colibri (not `dev`), DeepSeek V4.1 Flash REAP-192 MXFP4, CPU-only, 16 GB RAM, same NVMe drive, Windows 11: decode 1.11-1.14 tok/s from a RAW container against 0.98-1.01 from the safetensors (about +13%), TTFT 11-12 s against 13-14 s for 30 tokens. That fork reads a record with one read into one slab; `dev`'s V4.1 engine keeps six windows per expert, and this PR keeps them (section 4), so the number is the fork's, not a prediction for this PR. Nothing was measured on `dev` with the real model (section 9). The root and the per-record hash are new to the engine either way.

## 4. How it works

All in `c/deepseek_v41.c`:

```
model_load
  v41_wex_open        COLI_WEX_PATH unset -> return (nothing below runs); a GGUF's experts -> not used
                      st_open_fd: the container becomes the one file of its own shard set (wex->S),
                      with the O_DIRECT twin st.h opens for any shard
                      page 0 -> wex4_parse_header; grid == n_layers x n_routed?  COLI_WEX_ROOT == root?
                      index -> wex4_open; every EXPERT record: RAW, six tensors of the checkpoint's
                      shapes, part sizes and dtypes -> six st_tensor entries {fd, offset, size} per cell
                      (any failure: one "[v41_wex] ... ; the experts come from the safetensors" line)
miss (expert_slot_at / expert_slots_at -> expert_fetch)
  expert_read_list    a backbone expert the container holds -> its six entries, wex->S, replica 0;
                      otherwise the shards' tensors as before
  expert_fetch        unchanged reads, now through the entry's own shard set (ExpertRead.S):
                      the same windows, V41_READ_DEPTH reader threads, O_DIRECT where possible
  v41_wex_check       COLI_WEX_VERIFY, first read of a record: SHA-256 of its six parts in record
                      order plus its zero padding, against the index; mismatch -> this expert is read
                      again right there from the shards, and from the shards for the rest of the run
```

Why six reads and not one: the slot's six windows are separate allocations, each with the slack `st_read_range_rep` needs to make an unaligned range one O_DIRECT read. Reading the record whole would need either a seventh buffer and a copy of every expert (18.8 MB on REAP-192) or a new slot layout. Here the six reads are contiguous in one file and go through the existing readers; a one-read slot is left for series 4 (I/O), where it can be measured. The bytes: [WEX4-SPEC](https://github.com/KairaCode/Wex-WRN2/blob/main/docs/WEX4-SPEC.md).

## 6. How to use it

```sh
c/tools/wex4_verify v4_flash_experts.wex4    # once: prints COLI_WEX_ROOT=<root>
COLI_WEX_PATH=v4_flash_experts.wex4 COLI_WEX_ROOT=<root> ./deepseek_v41 <usual arguments>
```

| Variable | Default | Effect |
|---|---|---|
| `COLI_WEX_PATH` | unset | the container. **Unset: the engine reads exactly as on `dev`** (`v41_wex_open` returns at once, `v41_wex_has` is 0, every read goes through `&m->S` as before) |
| `COLI_WEX_ROOT` | unset | 64 hex digits; a container with another root is not used; turns `COLI_WEX_VERIFY` on |
| `COLI_WEX_VERIFY` | on with `COLI_WEX_ROOT`, else off | `1` / `0`: each record's SHA-256 at its first read |

At open: `[v41_wex] WEX4 container <file>: N of M experts, root <root>[ (pinned)]; first-read SHA-256 on|off`. A container is written by Wex-WRN2's `wex4/wex4_convert.py pack --experts raw` from the checkpoint's shards (a writer in colibri is open in #2860). Test containers built from real checkpoints are published at [Kaira666/Kaira-WEX4-Experts](https://huggingface.co/Kaira666/Kaira-WEX4-Experts) (its V4.1 file holds WNR3 records: series 2).

## 7. Compatibility and risk

- Without `COLI_WEX_PATH`: no behaviour change; the read list carries one more pointer per tensor (`&m->S`), and the verify pass is a NULL check per batch.
- The shards stay required and untouched: the dense weights, the engram tables, the DSpark stages, a missing or refused expert and the Vulkan tier's prewarm read them. The container is opened read only.
- Mirrors: `COLI_MODEL_MIRROR` still splits the shards' reads; the container's reads all go to replica 0 (series 4).
- A bad file never reaches a kernel: a damaged header page or index, a truncated copy, a WEX1-WEX3 file, another grid, another or a malformed root, records whose shapes, sizes or dtypes are not the checkpoint's, WNR3 records: not used, with a line. A record changed on disk: re-read from the shards at its first read when the check is on; with the check off it is served as it is (the shards would be too).
- Platforms: st.h's I/O, as for the shards (Linux, Windows, macOS). No CUDA, HIP or Vulkan code changed. The cluster worker (`EXPERT_WORKER=1`) does not open a container.

## 8. How to test

```sh
cd c
make tests/test_dsv41_wex4 && ./tests/test_dsv41_wex4 2>/dev/null
```

Passing prints:

```
  ok   no COLI_WEX_PATH: the shards, no container
  ok   WEX4 container: every expert it holds read from it, the one it lacks from the shards
  ok   its root pinned (first-read SHA-256 on): the same
  ok   layer 0 expert 2 changed on disk, pinned: refused at its first read, from the shards from then on
  ok   the same with COLI_WEX_VERIFY=1 and no pin
  ok   COLI_WEX_ROOT not 64 hex digits: no container
  ok   another root pinned: no container
  ok   a bit of the index changed: no container
  ok   a bit of the header page changed: no container
  ok   a truncated copy: no container
  ok   the WEX1 form: no container
  ok   a container of another grid (1 x 3): no container
  ok   records of other shapes and the same sizes: no container
  ok   COLI_WEX_PATH names no file: no container
test_dsv41_wex4: ok
```

Each case reads every expert of a synthetic checkpoint (2 x 3 experts, dim 64, moe_intermediate 32) through `expert_slot_at` with a one-slot cache (every expert read twice) and through `expert_slots_at` as one batch, compares the six matrices with the checkpoint's bytes, and checks how many experts the container served and refused. Without `2>/dev/null` the `[v41_wex]` lines show why each bad file was not used.

## 9. What I ran

- Windows 10, Intel i7-7700K, MSYS2 UCRT64 gcc 16.2, GNU make 4.4.1: `make deepseek_v41 tests/test_dsv41_wex4 tests/test_dsv41_engram_stage`, no warning from the changed or new code; both tests pass; `make check-env`: 863 variables, registry matches.
- Linux, Ubuntu 26.04 under WSL2, gcc 15.2: `make tests/test_dsv41_wex4 tests/test_dsv41_engram_stage tests/test_dsv41_scratch_pool`, no warning from the changed or new code; all three pass; again under ASan + UBSan with the `ASAN_OPTIONS` of `make test-asan`: all three pass.
- **Real expert records** (Windows 10, i7-7700K, one NVMe drive): the 192 experts of layer 0 of DeepSeek V4.1 Flash REAP-192 MXFP4 (dim 5120, moe_intermediate 2304, from its safetensors shard 3) and a WEX4 container packed from that shard with Wex-WRN2's `wex4/wex4_convert.py pack --experts raw` (3.75 GB, `tools/wex4_verify` passes). A scratch harness, not committed, reads every expert through `expert_fetch` in batches of 16, from the shards and then from the container with the root pinned: **192 of 192 experts byte-identical** in all six parts, 192 container reads, 0 refusals. One pass each: 12.4 s from the shards; from the container 24.6 s with the first-read SHA-256 on (portable SHA-256, no SHA extensions on this CPU; the check runs on the calling thread after a batch lands) and 8.1 s with `COLI_WEX_VERIFY=0`. The OS cache was not controlled (the container had just been written): not a speed comparison.
- Not run: the V4.1 tiny oracle (`tools/make_dsv41_tiny.py` needs torch, absent here; its experts are not in any container); a whole model run (the rest of DeepSeek V4.1 Flash REAP-192 was still downloading, and the published container of it holds WNR3 records, refused by this series); so no token comparison and no controlled speed number; macOS; the Vulkan and CUDA builds of the engine (none of their code changed).

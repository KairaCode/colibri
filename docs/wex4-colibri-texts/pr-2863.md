## 1. What this adds

DeepSeek V4's expert store can read its routed experts from a WEX4 container: `COLI_WEX_PATH=<file>`. A miss is then one aligned read of one record straight into the slot's slab, instead of six tensor ranges across the safetensors shards. `COLI_WEX_ROOT` pins the file's root and checks each record's SHA-256 the first time it is read. Anything that does not fit falls back to the safetensors, which stay open and stay the source of truth. Unset, nothing changes.

## 2. Why

One read per expert, page-aligned, already in the slab's layout: on DeepSeek V4.1 Flash REAP-192 MXFP4, CPU-only, 16 GB RAM, same NVMe drive, Windows 11, a downstream fork of colibri decoded at 1.11-1.14 tok/s from such a container against 0.98-1.01 from the safetensors (about +13%), TTFT 11-12 s against 13-14 s for 30 tokens. That fork's store is not `dev`'s and that model runs on `deepseek_v41` here, so the number says what the container did there, not what this PR does on `dev`; this PR has no speed measurement of its own (section 9).

The integrity part is new to colibri: with the root pinned the engine uses only the file that root names, and a record that was changed on disk after the root was taken is refused at its first read and served from the safetensors instead.

## 4. How it works

All of it is in `c/deepseek_v4.c`, in the expert-store unit (`COLI_V4_UNIT_EXPERT_STORE_HOT_ROWS16`, the store the engine links), in functions named `v4_wex_*`:

```
store open (coli_deepseek_v4_expert_store_open)
  v4_wex_open      COLI_WEX_PATH unset -> return, nothing else below runs
                   open(); read page 0; wex4_parse_header (wex4.h, #2862)
                   grid == the model's layers x experts?  COLI_WEX_ROOT set -> == the file's root?
                   read the index; wex4_open validates all of it in place
                   every EXPERT record: codec RAW? -> wex4_expert_entry -> a WexEntry per (layer, expert)
                   open an O_DIRECT twin (Linux O_DIRECT, Windows NO_BUFFERING, macOS F_NOCACHE)
  build_record     with a container, every record uses the per-matrix slab layout
                   (w1 w2 w3 scales, then w1 w2 w3 weights), the layout a WEX record already has
  v4_wex_bind      each container record vs its safetensors expert: shapes, sizes, offsets, GGUF no
                   any failure above -> one "[v4_wex] ... ; the experts come from the safetensors" line

miss (v4_read_expert_record, the base store's lookup, coli_v4_expert_store_read_private)
  v4_wex_read      not in the container, or refused before -> return 1: the safetensors path runs
                   pread the stored record (O_DIRECT twin when the slab is aligned) into slab[0]
                   padding after the expert's bytes must be zero
                   COLI_WEX_VERIFY and first read -> SHA-256 vs the index; mismatch -> refused for the run
                   any failure -> return 1: the safetensors path runs for this read

prefetch           a record the container serves is advised on the container (posix_fadvise WILLNEED),
                   not on the shard ranges
destroy            "[v4_wex] reads=... bytes=... fallbacks=... refused=..."
```

The slab already holds the record plus 16 KiB (`COLI_V4_EXPERT_SLAB_SLACK`), so a whole stored record (its expert's bytes rounded up to 4096) fits; it lands at the slab's first byte, nothing is moved after the read, and the tensor views are the per-matrix ones the store already has. The bytes of the file: [WEX4-SPEC](https://github.com/KairaCode/Wex-WRN2/blob/main/docs/WEX4-SPEC.md).

## 6. How to use it

```sh
c/tools/wex4_verify experts.wex4         # once, from a copy you trust: prints COLI_WEX_ROOT=<root>
COLI_WEX_PATH=experts.wex4 COLI_WEX_ROOT=<root> ./deepseek_v4 <usual arguments>
```

| Variable | Default | Effect |
|---|---|---|
| `COLI_WEX_PATH` | unset | the container. **Unset: the store is exactly `dev`'s** (no file opened, no layout change, `v4_wex_read` returns at its first line) |
| `COLI_WEX_ROOT` | unset | 64 hex digits; a container with another root is not used; turns `COLI_WEX_VERIFY` on |
| `COLI_WEX_VERIFY` | on with `COLI_WEX_ROOT`, else off | `1` / `0`: each record's SHA-256 at its first read |

The container must hold this checkpoint's routed experts (Wex-WRN2's `wex4/wex4_convert.py pack` writes one from the safetensors; a writer in colibri is open in #2860). At open the store prints `[v4_wex] WEX4 container <file>: N of M experts, root <root>[ (pinned)]; first-read SHA-256 on|off`.

## 7. Compatibility and risk

- Without `COLI_WEX_PATH`: no behaviour change; the new code is one NULL check per read and per prefetch key.
- Existing model files are not touched. The container is opened read only. The safetensors stay required: experts the container lacks or refuses come from them.
- With a container, every record uses the per-matrix layout (as REAP checkpoints already do). The rows16 repack, the GPU tier's mirrors and the private reads see the same slab layout they see for a REAP checkpoint.
- A bad file never reaches a kernel: a damaged header page or index, a truncated copy, a WEX1-WEX3 file, another grid, a root that is not the pinned one, records whose shapes differ from the checkpoint's, or WNR3 records: the container is not used, with a line saying which. A failed read or nonzero padding: that read is served from the safetensors. A record whose hash fails: that expert is served from the safetensors for the rest of the run.
- Platforms: plain `open`/`pread` (`compat.h` maps them on Windows), O_DIRECT twin where the OS has one. CPU code only; nothing changes in CUDA, HIP or Vulkan code. GGUF checkpoints: a container never matches a GGUF expert, so it is not used.
- Cost with `COLI_WEX_VERIFY=1`: one SHA-256 per expert, once per run (SHA-NI where the CPU has it).

## 8. How to test

```sh
cd c
make tests/test_v4_wex4 && ./tests/test_v4_wex4 2>/dev/null
```

Passing prints 15 `ok` lines and ends with:

```
ok   no COLI_WEX_PATH: the safetensors, no container
ok   WEX4 container: the 7 records it holds read from it, the 8th from the safetensors
ok   its root pinned (first-read SHA-256 on): the same
ok   record 2 changed on disk, pinned: refused at its first read, served from the safetensors
ok   the same with COLI_WEX_VERIFY=1 and no pin
ok   nonzero padding after record 3: never served (verify off)
ok   COLI_WEX_ROOT not 64 hex digits: no container
ok   another root pinned: no container
ok   a bit of the index changed: no container
ok   a bit of the header page changed: no container
ok   a truncated copy: no container
ok   the WEX1 form: no container
ok   a container of another grid (1 x 4): no container
ok   records of other shapes and the same sizes: no container
ok   COLI_WEX_PATH names no file: no container
test_v4_wex4: the WEX4 container serves the records it holds with the checkpoint's bytes; a bad, foreign or unpinned file is not used; a changed record falls back once its hash fails
```

Every case looks every expert up twice and compares the gate, down and up views, data and scales, with the checkpoint's bytes; each line also checks the container's read, fallback and refusal counts. Without `2>/dev/null` the store's `[v4_wex]` lines show why each bad file was not used. `make test-c` runs it on hosts where the V4 engine builds (x86-64 Linux and Windows, aarch64 Linux).

## 9. What I ran

- Windows 10, Intel i7-7700K, MSYS2 UCRT64 gcc 16.2, GNU make 4.4.1: `make tests/test_v4_wex4` (no warning from the changed or new code; the build's other warnings are `dev`'s, in `backend_loader_dsv4.c`), the test passes; `tests/test_deepseek_v4` on the same objects passes; `make check-env`: 863 variables, registry matches.
- Linux, Ubuntu 26.04 under WSL2, gcc 15.2: `make tests/test_deepseek_v4 tests/test_v4_wex4`, no warning from the changed or new code; both pass; again with `EXTRA_CFLAGS="-fsanitize=address,undefined -fno-sanitize-recover=all"` and the `ASAN_OPTIONS` of `make test-asan`: both pass.
- **Real expert records** (Windows 10, i7-7700K, one NVMe drive): the 192 experts of layer 0 of DeepSeek V4.1 Flash REAP-192 MXFP4 (its safetensors shard 3, 18,800,640 bytes an expert) and a WEX4 container packed from that shard with Wex-WRN2's `wex4/wex4_convert.py pack --experts raw` (3.75 GB, `tools/wex4_verify` passes). A scratch harness, not committed, opens this store on that shard as 1 layer x 192 experts and looks every expert up from the shards, then from the container with the root pinned: **192 of 192 experts byte-identical** (gate, down and up data and scales), 192 container reads, 0 fallbacks, 0 refusals. One pass each: 11.8 s from the shards; from the container 26.6 s with the first-read SHA-256 on (portable SHA-256: this CPU has no SHA extensions) and 7.6 s with `COLI_WEX_VERIFY=0`. The OS cache was not controlled (the container had just been written), so these times are not a speed comparison; they do show what the hash costs on a CPU without SHA-NI.
- Not run: a real DeepSeek V4 checkpoint (none on this machine; DeepSeek V4.1 runs on `deepseek_v41`, whose hook is a separate PR), so no speed or token comparison on a real model; macOS (the V4 engine does not build there); the CUDA, HIP and Vulkan builds of the engine (no code of theirs changed).

## 1. What this adds

Three header-only files, `c/wex_format.h`, `c/wex_palette.h` and `c/wex_neural_rans.h`, that define a WEX expert record: the 72-byte entry that says where a (layer, expert) record sits in the file and how its decoded bytes are laid out, the checks that bound every size and offset read from disk, and the lossless record codecs. One new test, `tests/test_wex_format.c`, runs in `make test-c`. No engine includes these files yet.

## 2. Why

They are the base of the WEX4 reader (next PR) and of the engine hooks after it. Kept separate so this PR is only the format and its test, and reviewed on its own.

The format's measured case, from a downstream fork of colibri (not `dev`): DeepSeek V4.1 Flash REAP-192 MXFP4, CPU-only engine, 16 GB RAM, same NVMe drive, Windows 11: experts from a RAW WEX container decoded at 1.11-1.14 tok/s against 0.98-1.01 from the safetensors (about +13%), TTFT 11-12 s against 13-14 s for 30 tokens. Details and the other numbers in #2860. Nothing here is measured on `dev`: this PR changes no engine.

## 4. How it works

A WEX record is the decoded bytes of one expert, padded to a 4096-byte page, in this order:

```
w1 scales | w2 scales | w3 scales | w1 weights | w2 weights | w3 weights
```

the order DeepSeek V4's per-matrix records and the Qwen3.8 MXFP4 sidecar records already use. `WexEntry` (72 bytes, `wex_format.h`) carries the record's file offset, its stored size, the six shapes and offsets inside the decoded slab, and a codec number. What reads a record:

- `wex_validate_header` / `wex_validate_table` / `wex_validate_entry`: every offset and size of the WEX1-WEX3 header and entry table checked against the file size and against each other before anything is allocated or read.
- `wex_entry_raw_sizes`: the decoded layout of an entry (scales, then weights, back to back), and its padded size.
- `wex_record_read_offset` and `wex_decode_record`: where to read a compressed record into the slab and how to expand it in place (codec 0 RAW: nothing to do; codecs 1-3: scale tiles, palette3, the first rANS form).
- `wex_decode_nr2_record` with `wex_nr2_model_open` (`wex_neural_rans.h`): the WNR2/WNR3 rANS decoder with its WNM2 model. WNR3 is series 2; the decoder is here because the WEX4 reader validates WNR3 records' sizes with it.

The bytes are specified in Wex-WRN2's [WEX4-SPEC](https://github.com/KairaCode/Wex-WRN2/blob/main/docs/WEX4-SPEC.md) and [WNR3-SPEC](https://github.com/KairaCode/Wex-WRN2/blob/main/docs/WNR3-SPEC.md).

The four C files are the copies kept in the Wex-WRN2 repository's `c/`, byte for byte apart from line endings (normalised to LF) and that repository's two-line licence header (not added here; colibri's files carry none). A format change goes there first, with the specification and the conformance vectors, and comes here as a PR.

Updated on 2026-11-16 to Wex-WRN2's current copies (this commit amended; the PRs stacked on it rebased, no other change to them): `wex_validate_table` now also bounds a WEX1/WEX2 header's `aligned_expert_bytes` by its table (at most twice the largest aligned decoded record, one page for a table without records; Wex-WRN2 commits bb48c0a and ce07b59), and `test_wex_format.c` gains `test_v12_slab_bound` for it. Also: one comment of `wex_neural_rans.h` that named the maintainer's private engine tree is reworded ("the same byte-renormalized state equations as a plain byte-wise rANS"), so the C files are Wex-WRN2's copies but for that comment, the line endings and the licence header. Only the WEX1-WEX3 validators change; no engine in this series reads those forms.

## 6. How to use it

Nothing to set. No environment variable, no flag, no default changes. The engines do not include the headers, so every engine behaves exactly as on `dev`.

## 7. Compatibility and risk

- No existing file's behaviour changes; the Makefile gains one test rule.
- Plain C99 headers with `static inline` functions; no allocation except inside the decoders, no I/O, no threads, no platform API. The palette's AVX2 path is compiled only with `__AVX2__`.
- A bad or truncated record: the validators return -1 before any byte of the destination slab is written; the test checks that for malformed streams and boundary sizes.

## 8. How to test

```sh
cd c
make tests/test_wex_format && ./tests/test_wex_format
```

Passing prints, last two lines:

```
WNR3 corruption audit: WNR2 11896 flips, 11300 rejected, 0 harmless, 596 WRONG accepted; WNR3+CZ 11304 flips, 11304 rejected, 0 harmless, 0 wrong accepted.
WEX format: V1/V2/V3, all bit widths, palette/scale boundaries, overlapping expansion, WNR2 round trips and malformed streams passed.
```

The first line is a measurement, not a failure: it flips single bits in synthetic records and counts what each decoder accepts. WNR2, the older codec, has no per-stream check and accepts 596 of 11,896 flipped records with wrong values; WNR3 rejects all 11,304. That is why WNR3 replaced it, and why series 2 brings WNR3 only.

`make test-c` runs it with the rest of the suite.

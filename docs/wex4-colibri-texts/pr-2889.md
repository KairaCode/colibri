Second PR of series 5. It changes `c/wex_decode.c` / `.h` and nothing in the engines.

Rebased on #2883's fix (the helper's workspaces pooled per call; this PR's commit is unchanged): the helper arms of section 9 now decode every record on the GPU, 8 tokens in 35.2 s on the CPU engine (was 57.9 s).

**Decisions** (the owner's, for #2888 and this PR):
- `wex_decode.c` stays included in each engine (as series 2 does) until the maintainer asks for a linked object.
- Kernel 2 (Wex-WRN2's AVX2 / SVE gather kernel) is left out: it was slower here.
- One thread per record in the engines: decoding one record on several threads gives 27 ms a V4.1 record on 8 threads, but no engine path needs it (the engines already decode several records at once).
- The fast decoder is on by default, because it is byte-identical to the reference and tested.

## 1. What this adds

`coli_wex_decode_record` decodes a WNR3 record on the CPU with the fast decoder of #2888 (`wex_fast_decode.h`) instead of the reference decoder, where the CPU has the fast decoder's kernel: AVX2 on x86-64 (by CPUID, with BMI1, BMI2, LZCNT and the OS's YMM state), NEON on ARM64. Same bytes, same refusals. `COLI_WEX_FAST_DECODE=0` keeps the reference. Every engine that reads WNR3 records through series 2's hooks (DeepSeek V4, Qwen3.8, DeepSeek V4.1) gets it through the one call it already makes.

## 2. Why

With the reference decoder, the published DeepSeek V4.1 REAP-192 WNR3 container ran about 4x slower than the shards on a CPU-only machine (#2879), because a record takes 740-800 ms to decode on one core. Measured here, the same conditions as series 2 (Windows 10, Intel i7-7700K 4 cores / 8 threads, CPU only, 8 expert slots, prompt "The three primary colors of light are", 8 greedy tokens, engram off, DSpark on as the checkpoint says, the checkpoint `DeepSeek-V4.1-Flash-REAP192-MXFP4` on a SATA SSD, root pinned so every record is hashed at its first read, one binary of this branch for every arm):

| experts from | WNR3 decoded by | prefill 8 tokens | decode 8 tokens | tok/s |
|---|---|---:|---:|---:|
| the shards (SATA), runs 1 / 2 / 3 | - | 60.2 / 63.5 / 64.4 s | 62.5 / 78.8 / 91.6 s | 0.13 / 0.10 / 0.09 |
| container on NVMe (Samsung 970 EVO Plus) | the reference (`COLI_WEX_FAST_DECODE=0`) | 209.4 s | 293.2 s | 0.03 |
| container on NVMe | **the fast decoder (default)** | 59.3 s | **71.1 s** | 0.11 |
| container on SATA | the reference | 211.9 s | 288.4 s | 0.03 |
| container on SATA | the fast decoder | 76.7 s | 87.6 s | 0.09 |

Every arm gave the same tokens, `6247 14 9214 14 14817 343 2869 288` (" Red, Green, Blue (noting"), as the shards and as series 2's run (shards 74.6 s, reference 293.6 s). The container arms read 37.5 GB against 43.7 GB from the shards (2,257 WNR3 records decoded, 0 refused). So the decoder is no longer the bottleneck: the container now runs at the shards' speed, within the shards' own run-to-run spread on this machine.

Per record (#2888's `--bench`, 16 records in memory, best of 3): 741.9 -> 101.2 ms on one thread (7.3x); 8 records at once, 125.5 -> 23.9 ms a record.

With the CUDA helper of series 3 and the Vulkan backend (section 9), for comparison: helper alone 35.2 s for the 8 tokens (0.23 tok/s; 57.9 s before #2883's workspace fix); the Vulkan chain (30 of 40 layers and a 16-expert tier on the RTX 3070) with the helper, 48.0 s (0.17 tok/s; 48.7 s before); same tokens.

## 4. How it works

```
coli_wex_register_model     a model added to the registry: on a CPU with the kernel (wexf_cpu_simd), its tables
                            (WexFastModel, 224 KiB, about 20 us) built beside it; NULL otherwise or without memory
coli_wex_decode_record(entry, slab, capacity)
  the record names its model (bytes 4..7) -> the registered model, as before
  the CUDA helper holds it (COLI_WEX_CUDA_LIB, series 3) -> the helper, as before; status 0: done
  a WNR3 record, the model's tables built, COLI_WEX_FAST_DECODE not 0
      -> wex_fast_decode_record(entry, slab, capacity, model, tables, {1 thread, kernel 1, 4 streams, fused})
         the same checks as wex_decode_nr2_record, scratch, the slab written only on 0
  otherwise (WNR2, no tables, COLI_WEX_FAST_DECODE=0) -> wex_decode_nr2_record, the reference, as before
first WNR3 record on the CPU  one line: "[wex] WNR3 records decode on the CPU with the fast decoder (AVX2; ...)"
                              or "... with the reference decoder (COLI_WEX_FAST_DECODE=0)" / "(the fast decoder
                              has no kernel for this CPU)"
```

One thread a record: the engines already decode several records at once on their reader threads (DeepSeek V4.1: one reader a record on the OpenMP team), and a decoder that started its own OpenMP team from a reader would compete with them. `COLI_WEX_FAST_DECODE` is read at each decode (one `getenv` beside a decode of megabytes). `coli_wex_cpu_decoder()` and `coli_wex_fast_decode_count()` report the choice and the count.

## 6. Variables and defaults

| Variable | Default | Effect |
|---|---|---|
| `COLI_WEX_FAST_DECODE` | `1` (on) | WNR3 records decoded on the CPU go to the fast decoder where the CPU has its kernel. **`0`: the reference decoder, exactly as series 2-4.** On a CPU without the kernel the value does not matter: the reference. |

On by default because the bytes and verdicts are the reference's (#2888's tests, and the engines' WEX tests with it on and off, section 9). Without `COLI_WEX_PATH`, or with a RAW container, nothing is decoded and nothing changes. Records the CUDA helper decodes never reach it.

## 7. Compatibility and risks

- Output: the same bytes as the reference for every record decoded, so the same tokens (section 2, every arm); a record the reference refuses is refused (#2888's mutation tests), and the engine then falls back as before (DeepSeek V4 / V4.1: the safetensors for that expert; Qwen3.8: stops, as it does for a damaged container).
- A bad file: unchanged handling; the fast decoder's checks are the reference's (stream hash, end of stream, canonical zero, ceil underflow), and the slab is untouched on -1.
- A CPU without AVX2 (or BMI2 / LZCNT, or an OS without YMM state): the registry builds no tables and every record takes the reference; checked with #2888's baseline build under `qemu-x86_64 -cpu Westmere`. colibri's x86-64 Windows default (`-march=x86-64-v3`) needs AVX2 anyway; a Linux `ARCH=x86-64` build carries the AVX2 kernel and picks it at run time.
- Memory: 224 KiB per registered model (at most 16), and the decode's scratch of one decoded record, as with the reference.
- Threads: no new threads; the decoder runs on the caller's thread. The registry builds the tables under its mutex before the model is published.

## 8. How to test

```sh
cd c
make tests/test_wex_fast_decode && ./tests/test_wex_fast_decode 2>/dev/null
```

Passing prints #2888's lines and, before the mutation test:

```
ok   coli_wex_decode_record: the fast decoder where the CPU has its kernel (COLI_WEX_FAST_DECODE unset or 1), the reference with COLI_WEX_FAST_DECODE=0; the reference's bytes, a damaged record refused and the slab as it was
test_wex_fast_decode: ok
```

The engines' WEX tests go through it: `make tests/test_wex_decode tests/test_v4_wex4 tests/test_qwen38_wex4 tests/test_dsv41_wex4`, each passing as before, and again with `COLI_WEX_FAST_DECODE=0`; their stderr says which decoder ran. With a model, the end-to-end run of section 2: `COLI_WEX_PATH=<v4_flash_experts.nr3.wex> COLI_WEX_ROOT=<root> ./deepseek_v41 ...` prints the `[wex] ... fast decoder (AVX2 ...)` line and the shards' tokens; `COLI_WEX_FAST_DECODE=0` the same tokens, slower.

## 9. What I ran

- Windows 10, i7-7700K, MSYS2 UCRT64 gcc 16.2: `test_wex_fast_decode` (three builds), `test_wex_decode`, `test_wex_cuda_loader`, `test_v4_wex4`, `test_qwen38_wex4`, `test_dsv41_wex4` pass with the variable unset and with `0`; `make check-env`: 865 variables, registry matches.

- **End to end**, section 2's table, every arm one run, the order: shards, container on SATA fast / reference, container on NVMe reference / fast / helper, then the Vulkan arms. The binaries were this branch's (the NVMe and Vulkan arms a build that only adds a stderr line with `coli_wex_cuda_decode_count()` and `coli_wex_fast_decode_count()` at the end, which gave the counts below).

  Vulkan placed 30 of the 40 layers on the card (5.3 GiB; the other 10 and the head on the CPU) and a 16-expert tier (707 MiB); what stopped more is the 8 GB: the chain fit leaves a 1 GiB reserve and 1.3 GiB of fixed buffers. In the first helper arms about a third of the records came back from the helper with status 1 and were decoded on the CPU by this PR's decoder: the helper leaked the workspaces of reader threads that exited until the 8 GB were full; #2883 now pools them per call (cause, evidence and test there), and the rows after the fix have every record on the helper. - Not run: a CPU without AVX2 natively (qemu only), a native ARM machine, macOS; Qwen3.8 and DeepSeek V4 on a whole model with a WNR3 container; DeepSeek V4.1's CUDA build (`CUDA_DLL=1`, an expert tier only for a safetensors checkpoint). Not relied on: colibri's CI.

**Update (fixed in this PR's commit): the status 1 records in whole-engine runs.** With #2884's loader, DeepSeek V4.1 runs sent about a third of the WNR3 records back to the CPU (helper / CPU: 1,500 / 757 with the CPU engine, 1,454 / 744 with Vulkan; #2889). The cause was here: each calling thread kept its own workspaces (`thread_local`), and the engine's reader team retires and respawns threads (at least 632 different reader threads called the helper in one 8-token run). The workspace destructor runs at thread exit, but there `cudaFree` fails with `cudaErrorDevicesUnavailable` (in the test below, instrumented: 768 of the 771 workspaces freed at thread exit; the other 3, at process exit, "driver shutting down"), so every exited thread kept its about 36 MiB of VRAM and its page-locked buffer. An instrumented helper showed 196 workspaces allocated by 196 different threads, free VRAM falling from 7.46 GB to 6 MiB, then 591 refusals in `ensure()` ("free 6291456 < 37601280"), exactly the 591 records the CPU decoded in that run. The fix: the workspaces (a single record's, a batch's 8 lanes) come from process-wide pools, taken for one call and given back, so the helper holds one per call in flight. New check in `test_wex_nr3_gpu`: 64 rounds of 4 fresh threads through all four entry points, every decode equal to the CPU's, and the device memory the helper holds must not grow; the previous helper fails it (1654 MiB more), this one passes (2-4 MiB). The same DeepSeek V4.1 runs now: CPU engine 2,257 / 0, 8 tokens decoded in 35.2 s (0.23 tok/s, was 57.9 s); Vulkan 2,198 / 0, 48.0 s (0.17 tok/s, was 48.7 s); same tokens (section 9).

## 1. What this adds

The optional CUDA helper that decodes WEX neural records (WNR1, WNR2 and WNR3) on an NVIDIA GPU, as a shared library an engine opens at run time: `c/tools/wex_cuda_bridge.cu` over the kernels in `c/wex_cuda.cuh`, built by `make wex-cuda-helper` into `kaira_wex_cuda.dll` (Windows) or `kaira_wex_cuda.so`, and its GPU test, `make wex-cuda-test`. Nothing in colibri opens it yet (the loader is the next PR). With no GPU, no CUDA toolkit, or no one running the new targets, nothing changes.

## 2. Why

A WNR3 record decoded by the CPU reference decoder costs about a second: on 16 records of the published DeepSeek V4.1 Flash REAP-192 container (18,800,640 decoded bytes each), 949-1010 ms per record on one thread of an Intel i7-7700K. The helper built by this PR decoded the same 16 records in 4.0-4.4 ms each through its host batch (8 records a call, pageable buffers) and in 5.9-9.4 ms each one at a time, on an RTX 3070 (sm_86, Windows 10), with bytes equal to the CPU decoder's (section 9). Without it, the published V4.1 container is not usable at decode speed.

The second reason is a fix: in Wex-WRN2's helper, `wex_cuda_decode_batch_to_host` queued each record's copy back to the caller's buffer right after its kernels, so a record that failed its integrity check had already been written to `dst[i]` when its status said -1. [WNR3-SPEC](https://github.com/KairaCode/Wex-WRN2/blob/main/docs/WNR3-SPEC.md) 4.7 says a refused record leaves the destination untouched, and Wex-WRN2's review lists this as an open finding. Here the host batch copies a record back only after the host has seen its error word. On real V4.1 records it is also faster than before: 3.03-3.06 against 4.20-4.23 ms per record for 8 records, 3.16-3.17 against 4.22-4.26 for 9 (section 9).

## 4. How it works

A record's path through the helper, for the entry points an engine uses:

```
wex_cuda_helper_abi() == 1, wex_cuda_helper_features() == 63      (bits: section 6)
wex_cuda_register_model(blob)          the WNM2 model, a private copy; device tables built per device on first use
wex_cuda_decode_to_host(entry, slab)   record at slab + wex_record_read_offset -> validate (wex_cuda_plan_nr2)
                                       -> upload on `stream` (head, then the weight payload) -> scale kernel, weight
                                       kernel on `aux` -> D2H into the call's private pinned buffer -> error word
                                       0? memcpy to the slab start : return -1, slab untouched
wex_cuda_decode_to_device(..., dst)    the same into private VRAM, then wex_cuda_launch_commit copies the six regions
                                       to the caller's device buffers only when the error word is 0
wex_cuda_decode_batch_to_device(n)     up to 8 lanes, every record queued, one host wait; the commit kernel per record
wex_cuda_decode_batch_to_host(n)       rounds of one record per lane: decode, wait, read the error words, copy back
                                       only the records whose word is 0, wait (this PR's change, wex_cuda_batch)
```

Every call returns 0 (decoded and written), -1 (invalid, or a failed per-stream hash, ceil-form or canonical-zero check: the destination is untouched) or 1 (CUDA or memory unavailable, or the model not registered). Workspaces (private streams, VRAM and page-locked scratch) come from process-wide pools: a call takes one and gives it back, so the helper holds one per call in flight, whichever threads call it; they are kept until the process exits.

## 6. Build, ABI and defaults

```sh
make -C c wex-cuda-helper CUDA_ARCH=sm_86     # Windows: from a vcvars64 shell (nvcc drives cl.exe), like cuda-dll
make -C c wex-cuda-test CUDA_ARCH=sm_86       # builds both, runs the synthetic part
```

| Bit | Export | What it adds |
|---|---|---|
| (ABI 1) | `wex_cuda_decode_to_host` | one record into a host slab |
| 1 | `wex_cuda_decode_to_device` | one record into caller-owned device buffers |
| 2 | `wex_cuda_host_register` / `_unregister` | page-lock a caller's buffer |
| 4 | `wex_cuda_register_model` | WNR2 records and the WNM2 model registry |
| 8 | `wex_cuda_decode_batch_to_device` | n records into device buffers |
| 16 | (none) | WNR3 records in every entry point |
| 32 | `wex_cuda_decode_batch_to_host` | n records into host buffers |

No environment variable. Nothing runs unless the library is built and, after the next PR, found. `make test-c` and every engine build are unchanged.

## 7. Compatibility and risks

- No engine source changes; the new targets are opt-in and need nvcc.
- A bad record never reaches a destination: every entry point refuses it with -1 and leaves the destination as it was; the device paths through the commit kernel, the host paths because the copy waits for the error word. The test checks this for each entry point on crafted and mutated records.
- One case can still leave part of a slab in a host batch's destination: a CUDA failure during the copy back itself (status 1); the slab is then part of a correct decode, and a caller treats any slot whose status is not 0 as empty.
- VRAM: the pooled workspaces are outside any backend's accounting: one per call in flight (on V4.1 records about 36 MiB per single-record call, 290 MiB per batch call), kept until the process exits; never one per thread that ever called.
- Below sm_80 `wex_cuda.cuh` replaces `cp.async` with plain loads; not run on such a GPU.
- The calls that take a device leave the calling thread on that device.

## 1. What this adds

The WNR3 encoder, so that a user can make the WNR3 containers the previous PRs read: `c/tools/wex_nr3_tools.c`, a small C library (`make wex-nr3-tools`) that prepares, trains, encodes and verifies one MXFP4 expert record with the reference codec of `wex_neural_rans.h`, and `c/tools/build_nr3.py`, the Python builder (standard library only) that drives it through ctypes. A test, `c/tests/test_wex_nr3_tools.py`, in the Python suite. No engine and no existing tool changes.

## 2. Why

Without it the only WNR3 containers a colibri user can run are downloaded ones. Measured here (Windows 10, i7-7700K, 8 threads): `build_nr3.py container` on a WEX1 file of 8 real DeepSeek V4.1 Flash experts (150 MB, layers 10 and 30 of the base checkpoint) wrote a WNR3 container of 132.4 MB (0.880 of RAW) in **3.6 s, training and the check decode of every record included**, and that file is **byte-identical** (same SHA-256) to the one Wex-WRN2's copy of the tool wrote from the same input with the same options. On 512 real Qwen3.8-Flash-Next experts (1.34 GB, one layer; the same reference encoder, through the test fixture of #2876) the records came to 0.878 of RAW.

## 4. How it works

Along the path of one record, `build_nr3.py ... container`:

```
Wex1(path)                    the source: a WEX1 container (RAW records, the 72-byte entry table)
get_model -> train            for each --train expert (or the 80 --train-lab80 picks over every layer):
                              wex_nr3_prepare (canonical zero with --cz, then the ceil form), 
                              wex_nr3_count_expert (the contexts the decoder uses), summed;
                              wex_nr3_build_model -> one WNM2 blob (59,408 bytes) and its id
run_parallel -> encode_one    8 threads, one record each:
                              wex_nr3_prepare -> wex_nr3_encode_record (wex_nr3_encode of
                              wex_neural_rans.h, weight chunks of 2048, scale chunks of 512, the
                              owner layer << 16 | expert in the record) -> padded to 4096;
                              not smaller than RAW -> kept RAW (codec 0)
                              wex_nr3_verify: decoded again on the CPU (wex_decode_nr2_record)
                              and compared with the source (its canonical-zero form for --cz)
mode_container                header page (WEX3, flags 33, 97 with --cz, the model's descriptor),
                              the blob at 4096, the table, the records; wex_nr3_check_container
                              (wex_validate_header / wex_validate_table of wex_format.h);
                              check_profiles (every record's CZ bit against the header);
                              written to OUT.partial, then renamed; OUT.json beside it
```

`bins` mode writes chosen records and the model in the layout of Wex-WRN2's GPU test tools, and `--save-model` keeps the model alone. The engines read WEX4, so the WEX3 file is made WEX4 in place by Wex-WRN2's `wex4/wex4_convert.py upgrade` (standard library; the records do not move), or a saved model goes to `wex4_convert.py pack --experts nr3`, which writes WEX4 straight from the safetensors with this library; `docs/wex.md` gives both routes. A WEX4 writer in colibri is still open (#2860).

## 6. How to use it

```sh
make -C c wex-nr3-tools
python3 -I c/tools/build_nr3.py c/tools/libwex_nr3_tools.so experts.wex container experts.nr3.wex \
        --layers all --train-lab80 [--cz] [--save-model model.wnm2]
python3 -I wex4/wex4_convert.py upgrade experts.nr3.wex       # Wex-WRN2: WEX3 -> WEX4 in place
c/tools/wex4_verify experts.nr3.wex                            # prints COLI_WEX_ROOT=<root>
```

No environment variable, no engine change: nothing behaves differently unless the tool is run. It reads its source read only, refuses to start without about 0.9 x the source plus 1 GiB free beside the output, and writes the output under a temporary name first.

## 7. Compatibility and risk

- New files and one Makefile target only.
- A record is written only after it decoded back to its source on the CPU; a record that would not be smaller stays RAW; the finished container's header, table and every record's canonical-zero bit are checked before it is renamed into place. A bad source (not WEX1, an entry that is not RAW) stops the tool with an assertion and leaves no output.
- `--cz` makes a value-exact container: the FP4 code -0 is stored as +0, the same values but not the same bytes, so the RAW records can then only be rebuilt from the checkpoint. Off by default.
- The test needs a C compiler (`$CC`, else `cc` or `gcc`) and skips without one; it builds its own copy of the library in a temporary directory.

It builds the library, writes a WEX1 file of 2 x 3 synthetic MXFP4 experts (dim 256, moe_intermediate 64), runs `build_nr3.py container` plain and with `--cz` and `bins --save-model`, checks the WEX3 header, that every record is WNR3 and smaller than its page, decodes every record back to its source with the library (and its canonical-zero form under `--cz`, where one expert carries -0 codes), and that a changed byte or another expert's name is refused. CI's Python job (`python3 -m unittest discover -s tests -p 'test_*.py'` in `c/`) picks it up.

## 9. What I ran

- Linux, Ubuntu 26.04 under WSL2, gcc 15.2, Python 3: `make wex-nr3-tools`, no warning; `python3 -m unittest tests.test_wex_nr3_tools`: 5 tests pass. then all eight WEX tests of the series (`test_wex_format`, `test_wex4_verify`, `test_wex_decode`, `test_v4_wex4`, `test_qwen38_wex4`, `test_qwen38_mxfp4_experts`, `test_dsv41_wex4`, `test_dsv41_engram_stage`) on the top of the stack under ASan + UBSan with `make test-asan`'s flags and options: all pass, no report; `make check-env`: 863 variables, registry matches. The whole `make -j8 test-c` on the last branch of the series (#2880, which holds this one; run before series 1's two include guards and three comments were reworded, no code differs): every gate passes but `test_uring`, whose "io-wq worker limit" check needs a kernel newer than the WSL2 one here (5.10), as in series 1; it shares no file with this series. Not relied on: colibri's CI (its runs are cancelled by design).
- **Real records**: `build_nr3.py container --layers 10,30 --train 10:0,...,30:3` on a WEX1 file of the 8 DeepSeek V4.1 Flash experts of layers 10 and 30 (4 each) of the base checkpoint, written earlier with Wex-WRN2's tools: 3.6 s, model `0x2a2e138e`, every record WNR3 (0 kept RAW), and the output's SHA-256 equals that of the WNR3 file Wex-WRN2's copy wrote from the same input (132,378,624 bytes, byte for byte).

## 1. What this adds

`COLI_MODEL_MIRROR` directories may hold a byte copy of the WEX4 container that `COLI_WEX_PATH` names, under the same file name. The copy becomes a read replica, and each expert's record is read from the drive the existing (layer, expert) hash picks, in the shares `COLI_DISK_WEIGHTS` sets: in `qwen38` (as its sidecar copies already are, #2824) and in `deepseek_v41`. The copy needs no checkpoint shards beside it. Opt-in: without `COLI_MODEL_MIRROR` nothing changes. Until now qwen38 printed that mirrors are not applied to a container, and deepseek_v41 sent every container read to the primary.

## 2. Why

A second drive adds read bandwidth for the experts that miss. Measured in a downstream fork of colibri (not `dev`), DeepSeek V4.1 Flash REAP-192, WEX4 container, RTX 5090, two NVMe drives (PCIe 4 and PCIe 5), one pair, 3 prompts x 64 tokens: decode 2.26 tok/s from one drive, 3.01 with the copy on the second (+34%), logits bit-identical ([BENCHMARKS](https://github.com/KairaCode/Wex-WRN2/blob/main/docs/BENCHMARKS.md)). For Qwen3.8 MXFP4 the same fork measured 11.48 against 12.45 tok/s (258-token prompt, one run each) with a mirror of its records.

On `dev`, this PR, `deepseek_v41`'s own expert reader (section 9): the 192 experts of one V4.1 layer read in batches of 6, O_DIRECT, Windows 10, from a SATA SSD alone at 516 MB/s, and at 1,797-1,883 MB/s once a copy on an NVMe drive was added (split 15/85 by the engine's probe), 3.5x, the same bytes. That NVMe drive alone read 2,472-2,719 MB/s, faster than any split of the two: the split pays when the drives are of comparable speed, or to add a fast drive to a container on a slow one, not to slow a fast drive down with a slow one. The docs say so.

## 4. How it works

```
st.h            st_mirror_add: a WEX4 file (magic "WEX4") is accepted when its size and its 4096-byte
                header page equal the primary's -- the page holds the index's SHA-256 and the root, so
                the index and every record offset match; a safetensors file keeps its header rule
                st_mirror_add_slot: the same, but the replica slot is taken even when the directory
                holds none of the set's files (they stay on the primary)

deepseek_v41    model_load: v41_wex_open first, then mirror_setup(&m->S, &m->wex->S, ...)
                mirror_setup: each COLI_MODEL_MIRROR directory registered on the shards AND on the
                container (st_mirror_add_slot on both; neither has a copy -> no replica), so replica r
                is the same drive for a shard tensor and for a container record; without
                COLI_DISK_WEIGHTS the probe reads the container's copy where there is one
                expert_read_list: a container record gets expert_route(layer, eid), as a shard tensor
                v41_wex_fetch_nr3: a WNR3 record (#2879) read whole from that replica too
                expert_fetch: st_read_range_rep(wex->S, fd, rep, ...): the replica's descriptor, O_DIRECT
                twin, the primary when the replica has no copy

qwen38          q38_wex4_attach -> q38_x4_mirrors(x, <the container's directory>, NULL): each directory
                itself is looked in (sub NULL), the shares and the refusal of a bad COLI_DISK_WEIGHTS are
                the sidecar's; q38_x4_read reads from q38_x4_replica's copy, as before
```

A record changed on the copy only is caught by `COLI_WEX_VERIFY` (on with a pinned root) at its first read there, and handled as on the primary: deepseek_v41 reads that expert from the shards, qwen38 stops.

## 6. How to use it

```sh
cp experts.wex4 /mnt/second/                     # a byte copy, the same file name
COLI_WEX_PATH=/mnt/first/experts.wex4 COLI_WEX_ROOT=<root> \
COLI_MODEL_MIRROR=/mnt/second COLI_DISK_WEIGHTS=1,1 ./deepseek_v41 ...
```

| Variable | Default | Effect with a container |
|---|---|---|
| `COLI_MODEL_MIRROR` | unset | `;`/`,`-separated directories; one holding a copy of the container (same name, size and header page) becomes a replica of it. **Unset: every record from `COLI_WEX_PATH`, as before** |
| `COLI_DISK_WEIGHTS` | deepseek_v41: probe at start; qwen38: equal shares | one positive weight per drive, primary first; qwen38 stops on a wrong count, deepseek_v41 probes instead |

No new variable. At open: `[MIRROR] <dir>: N/M shards, the WEX4 container (replica 1)` (deepseek_v41) or `[qwen38 MIRROR] <dir>: 1 of 1 files (replica 1)`, then the split.

## 7. Compatibility and risks

- Unset `COLI_MODEL_MIRROR`: no change; `mirror_setup` returns at its first line as before. With mirrors of the shards only, deepseek_v41 behaves as before too (the container slot of a directory without a copy reads the primary).
- A bad copy is not used: another size, another header page, a truncated file: `[MIRROR] ... size differs` / `header differs`, skipped. A copy with the right page and a damaged record: caught by `COLI_WEX_VERIFY` at its first read; with the check off, served as it is, as a damaged primary would be.
- The copy is opened read only and never written.
- Moving `mirror_setup` after `v41_wex_open` in deepseek_v41: nothing between them reads an expert or depends on the replicas (the GGUF geometry reads headers only).
- The route is the existing one, so an expert always comes from the same drive; the bytes are equal, so the tokens do not move.

## 9. What I ran

- Windows 10, Intel i7-7700K, MSYS2 UCRT64 gcc 16.2: the three tests above pass; no new warning (the one `st.h:713` format-truncation warning is `dev`'s).
- Linux, Ubuntu 26.04 under WSL2, gcc 15.2: `test_dsv41_wex4`, `test_qwen38_wex4`, `test_st_mirror`, `test_v4_wex4`, `test_dsv41_engram_stage` pass, and again under ASan + UBSan; `make -j8 test-c` on the tip of series 4: every test passes except `test_uring` (`io-wq worker limit`), which fails the same way on series 1's last commit: this WSL2 kernel (5.10) lacks it; `make check-env`: 864 variables, registry matches.
- **Real records**, Windows 10, i7-7700K, 32 GB: a RAW WEX4 container of the 192 experts of layer 0 of DeepSeek V4.1 Flash REAP-192 (3.75 GB, packed from its safetensors shard 3 with Wex-WRN2's `wex4/wex4_convert.py pack --experts raw`) on a SATA SSD, a byte copy on a Samsung 970 EVO Plus NVMe (deleted after). A scratch harness, not committed, opens `deepseek_v41`'s expert reader on the checkpoint as 1 layer x 192 experts and reads every expert through `expert_slots_at` in batches of 6 (6-slot cache, every read a miss), 3 passes per arm, timing the reads only; every arm's 192 experts hash to the same value as the shards' (`18c97b143034cf73`).

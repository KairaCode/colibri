## 1. What this adds

With `COLI_WEX_VERIFY` on (the default when `COLI_WEX_ROOT` pins the container), `deepseek_v41` hashes the RAW records of a batch of misses one expert a thread on the OpenMP team, instead of one after another on the calling thread after the reads. The same checks, the same fallback to the shards. WNR3 records (#2879) are already hashed by the reader thread that decodes them. With the check off, or a batch of one expert, nothing changes.

## 2. Why

`wex4.h`'s portable SHA-256 runs at about 200 MB/s a thread on a CPU without SHA extensions, and a V4.1 record is 18.8 MB, so the first read of a batch of 6 experts spent more time hashing than reading. On the 192 experts of one DeepSeek V4.1 Flash REAP-192 layer read from an NVMe drive through `deepseek_v41`'s expert reader (batches of 6, root pinned, Windows 10, Intel i7-7700K without SHA extensions), the first pass took 18.8 and 22.7 s before and 7.1 and 7.1 s after (-62% to -69%); the second pass, which hashes nothing, 1.4 s in every arm (section 9). Each record is hashed once per run, at the first use of its expert: for the 7,680 experts of the model that is 144 GB to hash, about 12 minutes of one such thread, spread over the first turns. On a CPU with SHA extensions (which `wex4.h` uses where it finds them) the gain is smaller; the downstream fork measured its own hash pool as neutral on such a machine.

## 4. How it works

In `expert_fetch` (`c/deepseek_v41.c`), after the reader threads have landed a batch:

```
for each expert i of the batch           #pragma omp parallel for schedule(dynamic, 1) if (hashing)
                                         hashing = COLI_WEX_VERIFY on and more than one expert
  not from the container -> next
  v41_wex_check (unchanged)              first read: SHA-256 of the six parts in record order + zero padding
    pass -> reads++ (atomic)
    fail -> state 2 (atomic), refused++; expert_read_list now names the shards' tensors;
            the six windows read again from the shards by this thread, as before
```

The loop runs on the default team width, as the read region above it does (a narrower team makes libgomp retire and respawn pool threads). Each iteration writes only its own expert's read list entries and slot.

## 6. Variables and defaults

No new variable. `COLI_WEX_VERIFY` (on with `COLI_WEX_ROOT`, else off) decides whether there is any hashing; `OMP_NUM_THREADS` sets the team as for the rest of the engine. Unset `COLI_WEX_PATH`, or the check off: the loop does no work, as before.

## 7. Compatibility and risks

- The checks and their outcome are the same: the same function, the same states, the same re-read; only the thread that runs them changes.
- A refused record is re-read from the shards inside the parallel loop: `st_read_range_rep` is already called from the reader threads, and each iteration reads into its own slot.
- Without OpenMP the loop is the serial one.

## 9. What I ran

- Windows 10, Intel i7-7700K (4 cores, 8 threads, no SHA extensions), MSYS2 UCRT64 gcc 16.2: `test_dsv41_wex4` and `test_dsv41_engram_stage` pass, no new warning.
- Linux, Ubuntu 26.04 under WSL2, gcc 15.2: the same tests, and under ASan + UBSan; `make -j8 test-c` on the tip of series 4: every test passes except `test_uring` (`io-wq worker limit`), which fails the same way on series 1's last commit: this WSL2 kernel (5.10) lacks it.
- **Real records**: the 192 experts of layer 0 of DeepSeek V4.1 Flash REAP-192 in a RAW WEX4 container (3.75 GB) on a Samsung 970 EVO Plus NVMe; a scratch harness, not committed, reading every expert through `expert_slots_at` in batches of 6 with the root pinned, 2 passes per arm (the reads timed, not the harness's own checksum), ABBA:

  | arm | first pass (hashes every record) | second pass |
  |---|---|---|
  | A1 before | 18.76 s | 1.42 s |
  | B1 this PR | 7.05 s | 1.58 s |
  | B2 this PR | 7.08 s | 1.39 s |
  | A2 before | 22.68 s | 1.42 s |
  | hash off | 1.95 s | 1.92 s |

  The same order from a SATA SSD that another job was also using: 28.95 / 22.32 s before, 14.26 / 13.12 s after.
- Not run: a whole model (no tok/s number of its own), a CPU with SHA extensions, macOS.

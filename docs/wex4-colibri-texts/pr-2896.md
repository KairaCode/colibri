# #2896: glm53: MXFP4 routed experts from a WEX4 container (COLI_WEX_PATH, COLI_WEX_ROOT), RAW and WNR3

Pull request https://github.com/JustVugg/colibri/pull/2896 (closed 2026-11-17, folded into the branch `kaira/wex4-colibri` of this fork). Head was `kaira/glm53-wex4-container @ 4b65bbaa`. Below: its description as written.

Part of #2860

## 1. What it adds

glm53 reads the routed experts of AMD's MXFP4 checkpoint from a WEX4 container instead of the shards: `COLI_WEX_PATH`, `COLI_WEX_ROOT` and `COLI_WEX_VERIFY`, RAW and WNR3 records through `coli_wex_decode_record`, and the CUDA helper when `COLI_WEX_CUDA_LIB` names it. It is the GLM-5.3 counterpart of the qwen38 hook (#2864, #2878), with the series' choices: `COLI_WEX_PATH` has no default, the helper loads only when `COLI_WEX_CUDA_LIB` is set, and a container that was asked for and does not hold stops the engine with the reason. The run ends with one line, `[glm53] WEX4 records: N read, M WNR3 decoded (CUDA helper H, CPU C)`.

## 2. Why

A container gives each expert one read of one record instead of six ranges of the shards, a SHA-256 for every record in an index whose hash is the root you pin, and, with WNR3 records, fewer bytes. On three real shards of the checkpoint (shards 3-5, 612 experts of layers 10-12, a WNM2 model trained on 80 of them, no canonical zero) the WNR3 expert records were 0.8893 of their decoded bytes, so an expert read is about 11% smaller; the whole container of the checkpoint is being built (its size goes into this PR when it is done). Decoding costs CPU instead: on the 4-core i7-7700K of that run the fast CPU decoder took 26-36 ms a record and the reference 611-773 ms, so on a CPU like that one WNR3 pays only with the CUDA helper or a slow disk (the Vulkan prototype decoded the same records in 0.82 ms on an RTX 3070). These are measurements of Wex-WRN2's tools on records, not of glm53.

**No whole-model GLM-5.3 run was done for this PR**: there was no engine A/B of the shards against the container. The only machine available has the checkpoint on a SATA SSD, and the owner chose not to run the whole model there; it is listed under "Tests wanted" in #2860. The hook is tested with synthetic containers (section 8).

## 4. How it works along a record's path

1. At load, after the shards' expert table, `g53_wex_maybe_attach` → `g53_wex4_attach` if `COLI_WEX_PATH` is set: the container opens as a file set of its own (`G53Wex.S`); the header page and the index are checked (`wex4_parse_header`, `wex4_open`); the grid must be the model's (45 x 288); `COLI_WEX_ROOT` (64 hex digits) must be the header's root; every expert record must have 6 tensors in the slab order (gate, down, up scales, then their codes), the release's shapes and offsets, dtypes U8/E8M0 and U8/I8; every expert of the loaded sparse layers must be there. WNR3 records: one WNM2 blob, checked against its SHA-256 in the index and registered (`coli_wex4_register_model`); all records value-exact or none.
2. `expert_read`, the one function every path takes an expert from (the CPU MoE, `expert_block_read` and the readahead, the Vulkan and CUDA tiers' loads and their warm start, the expert worker), hands the read to `g53_wex_read` when a container is attached.
3. `g53_wex_read` reads the record whole into the slot's own 4096-aligned memory (`O_DIRECT` under `G53_DIRECT`, as the shards' reads): a RAW record at offset 0, a WNR3 record's stored bytes at the end of its decoded page (`wex_record_read_offset`).
4. `COLI_WEX_VERIFY` (on with `COLI_WEX_ROOT`): the bytes as read and their zero padding against the index's SHA-256, at the record's first read.
5. A WNR3 record: `wex_nr3_owner_ok` (the owner and the canonical-zero flag), then `coli_wex_decode_record` in place: the CUDA helper first when `COLI_WEX_CUDA_LIB` names it, the fast CPU decoder (#2889) or the reference otherwise; a record the helper does not take (status 1) is decoded on the CPU.
6. The six pieces point into the decoded record; `expert_mats` builds the fmt 7 matrices exactly as for the shards. A record that fails its hash, names another expert or does not decode stops the engine.

## 6. Environment variables

| Variable | Default | Effect |
|---|---|---|
| `COLI_WEX_PATH` | unset | the container; unset, nothing changes and nothing of this PR runs |
| `COLI_WEX_ROOT` | unset | 64 hex digits: another root stops the engine; turns `COLI_WEX_VERIFY` on |
| `COLI_WEX_VERIFY` | on with `COLI_WEX_ROOT`, else off | each record's SHA-256 at its first read |
| `COLI_WEX_CUDA_LIB` | unset | the CUDA helper for WNR3 records; unset, no library is looked for |
| `COLI_WEX_FAST_DECODE` | on (#2889) | the fast CPU decoder for WNR3 records |
| `COLI_WEX_STATS` | unset (#2894) | `1`: at exit, which decoder took the WNR3 records |

With `COLI_WEX_PATH` unset the only change is the `if (m->wex)` at the top of `expert_read` and a NULL check at the end of a run.

## 7. Compatibility and risks

- The container is accepted only for an MXFP4 checkpoint (the previous PR); with the int4 container or a GGUF it is refused.
- The shards must still hold the experts: the shards' expert table is built first (and the non-expert weights are the shards' in any case).
- `COLI_MODEL_MIRROR` copies are for the shards; the container is read from its one path.
- Memory: each slot is the record's page (13,369,344 bytes), as the shards' slot.

## 9. What ran where

- Windows 10, i7-7700K, MSYS2 UCRT64 gcc 16.2.0: `make glm53` (no warnings); `tests/test_glm53_wex4` ok (30 checks, the fake helper cases included); `tests/test_glm53_mxfp4` ok; `tools/check_env_registry.py` ok.
- WSL2 Ubuntu, gcc 15.2.0: `tests/test_glm53_wex4` ok, plain and under ASan and UBSan (`detect_leaks=0`), no report.
- Compiled only (`-fsyntax-only`, no warnings): `glm53.c` with `-DCOLI_VULKAN`, and with `-DCOLI_CUDA -DCOLI_VULKAN`.
- The container format on the real checkpoint, with Wex-WRN2's tools (not glm53): on three shards, `pack --experts nr3 --names qwen38`, both verifiers on the root, `unpack` byte-identical, every record decoded equal to the shards' bytes by the reference and the fast decoder, the CUDA helper (0dc53c2a) on 8 records and the Vulkan prototype on 10; the whole container: being built.
- **Not run:** glm53 on the whole checkpoint, from the shards or from the container, with or without the helper; the Vulkan and CUDA tiers with container records. The record layout glm53 checks at attach (offsets, shapes, dtypes) is the one those containers have, but no glm53 process opened them.

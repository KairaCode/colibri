## 1. What this adds

`c/wex_fast_decode.h`: a CPU decoder of WNR3 records that gives the bytes of the reference decoder (`wex_nr2_decode` of `wex_neural_rans.h`, which `wex_decode.c` uses) and refuses the same records, about 7x faster on one x86 core. It is Wex-WRN2's research decoder (`wex4/research/fast-cpu-decode/`, whose RESULTS.md has its own validation) with its kernels 0 (the reference loop, stream by stream) and 1 (AVX2 and NEON), the AVX2 kernel chosen at run time, and one slab-level call added. `c/tests/test_wex_fast_decode.c` checks it against the reference in three builds, in `make test-c`. Nothing calls the header yet; the next PR makes `coli_wex_decode_record` use it.

## 2. Why

With series 2, DeepSeek V4.1 runs the published WNR3 container (REAP-192) end to end, but on the CPU the reference decoder is the bottleneck: on a 4-core i7-7700K, CPU only, 8 expert slots, 8 greedy tokens, it decoded 8 tokens in 293.6 s against 74.6 s from the shards (#2879). A V4.1 record (18,800,640 decoded bytes) takes the reference 742 ms on one thread.

Measured here with this PR's `--bench` (Windows 10, i7-7700K, MSYS2 UCRT64 gcc 16.2, the default `-O3 -march=x86-64-v3`, 16 records of the published container spread over its layers, read into memory first, best of 3 passes):

| decoder | 1 thread, ms/record | 8 threads in one record | 8 records at once, ms/record |
|---|---:|---:|---:|
| reference (`wex_decode_nr2_record`) | 741.9 | - | 125.5 |
| fast (`wex_fast_decode_record`, AVX2 kernel 1, 4 streams, fused) | 101.2 (7.3x) | 27.0 | 23.9 (5.3x) |

The same bench with the container on an NVMe drive (records still read into memory first, so the drive does not enter the times): 802.1 / 146.9 ms for the reference, 106.1 / 33.5 / 28.5 ms for the fast decoder. The whole-model effect is measured in the next PR, where an engine uses it.

## 4. How it works

The path of one WNR3 record through `wex_fast_decode_record(entry, slab, capacity, model, tables, options)`:

```
the same checks as wex_decode_nr2_record   entry sizes, read offset, wex_nrx_parse of the record at the end of its page
scratch of the decoded size               decoded there, copied to the slab only on 0 (slab untouched on -1)
wex_fast_decode_with(tables, view, ...)
  scale streams, then weight streams      the u16 lengths prefix-summed into at most 256 task offsets (no allocation);
                                          tasks in parallel only when options.threads > 1 (OpenMP)
  kernel 1 (AVX2 or NEON)                 4 streams of one matrix and the same count decoded in one loop;
    weights                               each (matrix, srel, maximum, previous) context a 128-byte entry
                                          {upper, start, freq, next}[16]: one AVX2 compare of the slot with upper[]
                                          + tzcnt is the symbol (NEON: two 8-lane compares), next[] the next context;
                                          branchless renormalisation; stream hash and ceil inverse fused in the loop
    scales                                a 16,384-entry slot -> symbol table per matrix
  kernel 0                                the reference loop with its per-byte end check: streams within 104 bytes of
                                          the payload's end, counts not a multiple of 32, a CPU without the kernel
  each stream                             ends exactly at its end, with the 23-bit hash state the reference checks;
                                          canonical-zero and ceil-underflow checks as the reference -> else -1
```

A stream that runs past its end is noticed at the next 32-symbol boundary instead of at the byte; the read pointer only grows, so that is the same verdict as the reference's, and the slack rule keeps every read inside the payload. The tables (`WexFastModel`, 224 KiB) are built once per model by `wex_fast_model_init` (about 20 us).

**Which kernel.** x86-64 with GCC or clang: the AVX2 kernel is compiled in every build, with `__attribute__((target("avx2,bmi,bmi2,lzcnt")))` when the build does not target AVX2, and runs only when CPUID says the CPU has AVX2, BMI1, BMI2 and LZCNT and the OS saves the YMM state (OSXSAVE, XCR0); otherwise kernel 0. Little-endian AArch64: the NEON kernel (base instruction set). Other targets, or `-DWEX_FAST_SCALAR`: kernel 0. `wex_fast_kernels()` says which.

What is not carried from Wex-WRN2: its kernel 2 (AVX2 gathers, and an SVE version), slower than kernel 1 on the CPUs measured there and never its default; no licence header. The API names are Wex-WRN2's (`wex_fast_decode`, `wex_fast_decode_with`, `wex_fast_model_init`, `WexFastOptions`), plus `wex_fast_decode_record` and `wex_fast_kernels`.

## 7. Compatibility and risks

- Bytes and verdicts: the test compares every variant (kernel 0; kernel 1 with 1, 2, 3, 4, 6 and 8 streams, fused or not; 1 and 8 threads) with the reference on synthetic and real records, and on mutated mini-records: status and bytes equal in every case run (section 9).
- A bad record: refused as by the reference (the mutation test reaches the canonical-zero check, the ceil-underflow check, the end-of-stream check and the stream hash with records whose hashes are right); `wex_fast_decode_record` leaves the slab as it was on -1, as `wex_decode_nr2_record` does.
- Memory safety: every buffer of the test sits against a page without access (the record without its padding flush against the upper guard, outputs flush against either guard, the model too); no fault in any run, and none under ASan + UBSan or clang's UBSan trap build.
- A CPU without AVX2 (or without BMI2 / LZCNT, or an OS that does not save YMM): the CPUID check sends every stream to kernel 0; checked under `qemu-x86_64 -cpu Westmere` (section 9). A binary built for x86-64-v3 (colibri's Windows default) needs AVX2 anyway.
- Compilers: GCC and clang (`target` attribute, `<cpuid.h>`, inline `xgetbv`). Another compiler on x86-64 gets kernel 0 only.
- Big-endian targets: kernel 0 only (the SIMD paths assume little-endian).

## 8. How to test

```sh
cd c
make tests/test_wex_fast_decode && ./tests/test_wex_fast_decode
```

Passing prints (on an AVX2 CPU):

```
     fast decoder: kernel 1 on AVX2 here (WEX_FAST_LANES 4)
ok   synthetic WNR3 records (plain and canonical zero, 6 chunk sizes): every variant on 1 and 8 threads, the default entry point and the slab-level call give the reference's bytes
     512 single-bit changes of a record: 512 refused by both, 0 decoded by both to the same bytes, 0 differ
ok   another model, a slab one byte short, 512 single-bit changes (the first 128 bits, then sampled): the same status as the reference, the same bytes, a refused record leaves the slab as it was
     synthetic, plain model: 150 records at the decoders (...); ... 0 mismatches
     synthetic, CZ model: 150 records at the decoders (...); ... 0 mismatches
ok   mutation test on synthetic mini-records: same status as the reference, same bytes when both accept
test_wex_fast_decode: ok
```

`tests/test_wex_fast_decode_x86_64` and `tests/test_wex_fast_decode_scalar` print the same (the scalar one says `kernel 1 on scalar`). `make test-c` runs all three (about 7, 7 and 17 s here). On real records, with a WNR3 WEX4 container (the published V4.1 one, for instance):

```sh
./tests/test_wex_fast_decode --mutate 3000 v4_flash_experts.nr3.wex 8   # 8 records, 3,000 mini-records cut from them
./tests/test_wex_fast_decode --bench v4_flash_experts.nr3.wex 16        # the table of section 2
```

## 9. What I ran

- Windows 10, i7-7700K, MSYS2 UCRT64 gcc 16.2: the three builds pass, no warning. clang 23.1 (without OpenMP: UCRT64's clang has no `omp.h`) with `-march=x86-64`, with `-march=x86-64-v3`, and with `-fsanitize=undefined,bounds -fsanitize-trap=all`: pass, no warning.
- **Real records**, the published DeepSeek V4.1 Flash REAP-192 WNR3-CZ container (root `f0f78a84…eeb1`, SATA SSD): 8 records (L2 ... L37, one every 5 layers) through every variant on 1 and 8 threads, the default entry point and the slab-level call: equal; 3,000 mini-records cut from them, encoded with the container's model, then damaged: 3,000 at the decoders, 794 accepted and 2,206 refused by the reference, 39,000 fast decodes, 0 mismatches. The `-march=x86-64` build: 2 more records and 1,000 mini-records, 0 mismatches. The same run's 1,500 + 1,500 synthetic mini-records (plain and canonical-zero model): 0 mismatches. The `--bench` table of section 2.
- Linux, Ubuntu 26.04 under WSL2, gcc 15.2: the three builds, `test_wex_decode`, `test_wex_format` pass; 2 real records (read from the Windows drive) and 1,000 mini-records: 0 mismatches.
- **A CPU without AVX2**: the `-march=x86-64` build under `qemu-x86_64 -cpu Westmere` (qemu 10.2): `kernel 1 on scalar here`, passes; under `-cpu Haswell` it takes the AVX2 kernel and passes.
- **NEON**: cross-built with aarch64-linux-gnu-gcc 15.2 (`-O3 -fopenmp -static`) and run under `qemu-aarch64`: `kernel 1 on NEON here`, the synthetic records and 600 mini-records pass, and 1 real record (L20 E0) plus 300 mini-records cut from it with the container's model: 0 mismatches; the `-DWEX_FAST_SCALAR` ARM build passes too. Wex-WRN2's CI runs the same NEON kernel natively (`linux-arm`, Neoverse-N2, and Apple M1 VMs; its RESULTS.md).
- ASan + UBSan (WSL2, gcc 15.2, `make test-asan`'s flags): the three builds pass, no report (run on the next PR's branch, which holds this one).
- Not run: a native ARM machine (qemu only here), macOS, MSVC. Not relied on: colibri's CI.

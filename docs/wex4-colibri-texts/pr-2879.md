## 1. What this adds

`deepseek_v41` reads WNR3 (codec 5) records from the WEX4 container `COLI_WEX_PATH` names, as well as the RAW records of #2865. With it, **the published DeepSeek V4.1 Flash REAP-192 container (7,680 WNR3 records, 123.3 GB) runs end to end**: the trunk from the checkpoint's shards, the backbone's routed experts from the container, decoded on the CPU. A record that fails is read from the shards for the rest of the run, as with #2865. Unset, nothing changes; a RAW container reads exactly as with #2865.

## 2. Why

This is the model the WNR3 container was made for, and #2865 had to refuse it. Measured here, the whole engine, end to end (section 9 for every condition): Windows 10, Intel i7-7700K (4 cores), 32 GB RAM, the checkpoint and the container on one SATA SSD (Crucial BX500), CPU only, `deepseek_v41 8` (8 expert slots per layer), an 8-token prompt and 8 greedy tokens, the engram tables absent (they are not part of the REAP repository) so engram is off in both runs:

| | prompt (8 tokens) | 8 generated tokens | expert bytes read | tokens |
|---|---:|---:|---:|---|
| shards (`dev`'s path) | 102.4 s | 74.6 s (0.11 tok/s) | 43.7 GB | ` Red, Green, Blue (noting` |
| WNR3 container, root pinned, first-read SHA-256 on | 232.8 s | 293.6 s (0.03 tok/s) | 37.5 GB | the same 8 ids |
| WNR3 container, root pinned, `COLI_WEX_VERIFY=0` | 209.0 s | 314.3 s (0.03 tok/s) | 37.5 GB | the same 8 ids |

The same 1,547 cache hits and 2,323 misses in every run (2,257 of them experts the container served and decoded, 0 refused; the rest the DSpark stages', from the shards). So on this machine the CPU decode is the bottleneck: 14% fewer bytes from the drive, about 3x the time. That is the expected shape on a 4-core CPU with the reference decoder (761 ms per 18.8 MB expert per core, #2876): the WNR3 container is usable on the CPU and gives the same tokens, it is not faster there. The GPU decode (series 3) is what made it 2.92-2.96 tok/s in the downstream fork (#2860); none of that is in this PR.

## 4. How it works

All in `c/deepseek_v41.c`, on #2865's hook:

```
model_load
  v41_wex_open        as in #2865: header page, index, grid (n_layers x n_routed), COLI_WEX_ROOT,
                      every expert record with the checkpoint's six shapes, part sizes and dtypes
                      WNR3 records: wex4_expert_entry -> wex->nr3[cell], and the six st_tensor
                      entries hold each part's offset inside the decoded record (RAW: in the file);
                      one WNM2 blob, all or none value-exact; the blob read -> coli_wex4_register_model
                      (any failure: one "[v41_wex] ... ; the experts come from the safetensors" line)
miss (expert_slot_at / expert_slots_at -> expert_fetch)
  expert_read_list    unchanged: a backbone expert the container holds -> its six entries, wex->S;
                      each read now carries its expert id (ExpertRead.eid)
  expert_fetch        RAW: as in #2865, six reads into the six windows
                      WNR3: the reader that takes the expert's first part calls v41_wex_fetch_nr3;
                      the expert's other five reads do nothing
  v41_wex_fetch_nr3   the stored record read whole into a pooled page at the end of its decoded size
                      (one O_DIRECT read: offset and length are pages); COLI_WEX_VERIFY, first read:
                      SHA-256 of the stored bytes; wex_nr3_owner_ok; coli_wex_decode_record in place;
                      each part copied to its window at the offset expert_fetch publishes
                      (its offset in the record mod ST_DIRECT_ALIGN, inside the window's slack)
                      any failure -> v41_wex_refuse: state 2
  after the readers   as in #2865: a RAW record hashed (v41_wex_check); a WNR3 record in state 2 is
                      read again right there from the shards, and from the shards for the rest of the run
end of an argv run    [v41_wex] container: N records read (M WNR3 decoded), K refused
```

The decode runs on `V41_READ_DEPTH` reader threads (8 by default), so up to 8 records decode at once, each with one pooled page (18.8 MB on REAP-192) and the decoder's own scratch of the same size. The windows, the publish step, the GPU tiers and everything after the read are #2865's; they see the decoded bytes.

## 6. How to use it

```sh
c/tools/wex4_verify v4_flash_experts.nr3.wex     # once: prints COLI_WEX_ROOT=<root>
COLI_WEX_PATH=v4_flash_experts.nr3.wex COLI_WEX_ROOT=<root> SNAP=<checkpoint> ./deepseek_v41 <usual arguments>
```

For the published REAP-192 container the root is `f0f78a84d040a3b336f3abef3cf8b0a36c649deb38586c813e94d35dea3beeb1`. No new variable: `COLI_WEX_PATH`, `COLI_WEX_ROOT`, `COLI_WEX_VERIFY` keep #2865's defaults and meanings. **Unset `COLI_WEX_PATH`: the engine reads exactly as on `dev`** (`v41_wex_open` returns at once; `v41_wex_nr3` is NULL for every read). At open the line gains `(N WNR3, model <id>[, value-exact])`.

## 7. Compatibility and risk

- Without `COLI_WEX_PATH`, or with a RAW container: no behaviour change; each read list entry carries one more int.
- The shards stay required: the dense weights, the DSpark stages, a refused expert and the Vulkan tier's prewarm read them.
- A bad file never reaches a kernel: a model blob that does not match the index, WNR3 records of two models, mixed value-exact: not used, with a line. A WNR3 record changed on disk is refused by its stream checks (hash off) or its SHA-256 (hash on); a whole record under another expert's name by its owner; each time that expert is read again from the shards and stays on them. The test covers each.
- Value-exact (canonical-zero) records decode -0 as +0, the same values; the published container is value-exact and gave the same tokens as the shards.
- Cost: CPU time on the reader threads and up to `V41_READ_DEPTH` x 2 x 18.8 MB of buffers while decodes run (the pooled pages stay in the reader pool, as the GGUF path's do).

- **End to end on the real model** (Windows 10, i7-7700K 4 cores / 8 threads, 32 GB RAM, RTX 3070 not used, checkpoint and container on one Crucial BX500 SATA SSD, this branch's `deepseek_v41` built CPU-only with MSYS2 gcc): `SNAP=<DeepSeek-V4.1-Flash-REAP192-MXFP4> ./deepseek_v41 8 ref.json` with `ref.json` = BOS + the 7 tokens of "The three primary colors of light are" and 8 output tokens, three runs one after the other: without `COLI_WEX_PATH`, with the published WNR3 container and its root pinned (first-read SHA-256 on), and the same with `COLI_WEX_VERIFY=0`.

## 1. What this adds

`c/wex_decode.c` and `c/wex_decode.h`: the CPU side of WNR3 records (codec 5). A WNR3 record is an MXFP4 expert record coded losslessly with rANS against a model the whole container shares (a WNM2 blob of 59,408 bytes). This file keeps the process's registry of those models and decodes one record in place into the slab the expert kernels already read. A test, `tests/test_wex_decode.c`, and a test helper, `tests/wnr3_fixture.h`, that writes WNR3 records and the WNR3 form of a WEX4 container with the reference encoder. No engine calls the new code yet; the next three PRs do.

## 2. Why

WNR3 makes an expert container smaller with no change to a single value. The published DeepSeek V4.1 Flash REAP-192 container ([Kaira666/Kaira-WEX4-Experts](https://huggingface.co/Kaira666/Kaira-WEX4-Experts), `v41-reap/`) holds its 7,680 experts as WNR3 records: 123.3 GB against 144.4 GB as RAW records (0.854). That file is the one #2865 cannot use today.

Measured here (Windows 10, Intel i7-7700K 4 cores / 8 threads, MSYS2 UCRT64 gcc 16.2 `-O2`): the reference decoder of `wex_neural_rans.h`, which this PR uses, decodes a DeepSeek V4.1 expert (18,800,640 bytes) in **761 ms on one thread (24.7 MB/s)**, and 8 experts at once in about 977 ms each (about 155 MB/s for the CPU). That is slow next to a drive, so on the CPU WNR3 is a trade of disk bytes for CPU time; the GPU decode (series 3) is where it pays. The numbers are from the scratch harness in section 9.

## 4. How it works

The life of a WNR3 record, with the functions an engine calls:

```
container open      the WEX4 index names one WNM2 blob for the WNR3 records (wex4_open checked its size)
  engine            reads the blob's page(s) from the file
  coli_wex4_register_model(bytes, n, stored, sha, id)
                    SHA-256 of the blob against the index, zero padding, the model id the index gives
                    -> coli_wex_register_model: wex_nr2_model_open validates the CDFs; a copy is kept
                    for the life of the process (16 models at most; the same blob again is a no-op;
                    another blob with the same id is refused)
miss                the record's stored bytes read at slab + wex_record_read_offset(entry), the end
                    of its decoded page (so the decode can run in place)
  wex_nr3_owner_ok  (wex_format.h) the record's owner (layer << 16 | expert) and canonical-zero flag
                    against what the engine asked for
  coli_wex_decode_record(entry, slab, capacity)
                    the record names its model at bytes 4..7 -> the registered model ->
                    wex_decode_nr2_record (wex_format.h): parse, decode into scratch, every rANS
                    stream checked against its 23-bit hash, the ceil form undone -> the slab starts
                    with the decoded record (scales, then weights); on -1 the slab is not used
```

A canonical-zero (CZ) record stores the FP4 code -0 as +0: it decodes to the same values, not the same bytes; its container marks such records value-exact. `coli_wex_container_refused` keeps Wex-WRN2's rule that a value-exact container is not used under `DSV4_CUDA_MOE_MASKED=1` (the masked MoE path, not proven value-exact); the DeepSeek V4 hook calls it.

Wex-WRN2's `c/wex_decode.c` also loads an optional CUDA helper (`kaira_wex_cuda.dll`) that decodes on the GPU. That part is left out, not stubbed: this file has no CUDA symbol, no `COLI_WEX_CUDA_LIB`, no `LoadLibrary`. Series 3 adds it. The API names are Wex-WRN2's, so that PR adds functions and changes none.

**Linking.** The engines that read WEX4 are each one translation unit (qwen38, deepseek_v41) or keep their whole expert store in one unit (deepseek_v4's `COLI_V4_UNIT_EXPERT_STORE_HOT_ROWS16`), and the segment adapters link qwen38 and DeepSeek V4 into one library. So an engine includes the file with `#define COLI_WEX_DECODE_API static inline` / `#include "wex_decode.c"`: each engine has its own registry, the container registers and decodes in the same unit, and no symbol is defined twice. Compiled alone (`cc -c wex_decode.c`) the functions are external. No Makefile link line changes.

## 7. Compatibility and risk

- No existing file changes but the Makefile (one rule) and the docs.
- A bad model blob: refused before it is registered (wrong SHA-256, nonzero padding, another id, CDFs `wex_nr2_model_open` rejects). A bad record: `coli_wex_decode_record` returns -1 and the caller must not use the slab; the test flips 4,608 single bits of a record (all of its first 64 bytes, 4,096 sampled elsewhere) and every one is refused, none decodes to other bytes. A record of a model that was not registered: -1.
- Threads: the registry takes a mutex to add or find a model and never frees one, so a found model stays valid; the decode itself holds no lock and allocates its own scratch (the decoded size, freed on return). 8 threads decoding the same record at once agree.
- Memory: a decode takes one buffer of the decoded size while it runs (18.8 MB for a V4.1 expert); the registry keeps 59,408 bytes per model.
- Platforms: plain C with pthreads, as the engines already use; no SIMD, no OS API.

**Decisions** (taken for this series, recorded here):

- `wex_decode.c` is included by each engine with `COLI_WEX_DECODE_API static inline` (no Makefile link changes, see "Linking" in section 4). If you prefer it as a linked object (`wex_decode.o` on the engines' link lines, external functions), say so and it changes in this PR; the API does not change.
- A container whose WNR3 records are partly value-exact (canonical zero) and partly not is refused, on purpose: the three hooks of this series do not use it ("has WNR3 records both value-exact and not (all or none are read)"). They check one canonical-zero form for the whole container (the flag `wex_nr3_owner_ok` is given), so a mixed file is treated as a bad file, not served record by record.

## 8. How to test

```sh
cd c
make tests/test_wex_decode && ./tests/test_wex_decode 2>/dev/null
```

Passing prints:

```
ok   an invalid model blob is refused; a valid one registers and returns its id
ok   the same blob again: the same id, nothing added
ok   coli_wex4_register_model: the index's blob registers; another SHA-256, nonzero padding or another id do not
ok   a WNR3 record decodes in place to the record it was made from
ok   a canonical-zero record decodes to the record with -0 stored as +0
ok   a RAW entry: nothing to do, the slab is the record
ok   a record whose model is not registered: refused
     4608 single-bit changes: 4608 refused, 0 decoded to the right record anyway, 0 wrong
ok   every bit of the first 64 bytes and 4,096 sampled bits elsewhere changed one at a time: never a wrong record
ok   8 threads decoding the same record at once: all right
ok   coli_wex_container_refused: a canonical-zero container under DSV4_CUDA_MOE_MASKED=1 only
ok   the WNR3 form of a WEX4 container, plain and canonical zero: it opens, its blob registers, every record decodes to its RAW record
ok   16 models fit; a 17th is refused, one already registered is still found
test_wex_decode: ok
```

The records are synthetic (64 x 256 MXFP4 matrices, 26,112 bytes) and made by the reference encoder of `wex_neural_rans.h`. `make test-c` runs it with the rest.

- Windows 10, Intel i7-7700K, MSYS2 UCRT64 gcc 16.2, GNU make 4.4.1: `make tests/test_wex_decode`, no warning; passes. `tests/test_wex_format` and `tests/test_wex4_verify` pass on this branch. Also built with clang 23 `-fsanitize=undefined,bounds -fsanitize-trap=all`: passes.
- Linux, Ubuntu 26.04 under WSL2, gcc 15.2: each branch of the series built and tested on its own (this one: `make tests/test_wex_format tests/test_wex4_verify tests/test_wex_decode`, no warning, all three pass); then all eight WEX tests of the series (`test_wex_format`, `test_wex4_verify`, `test_wex_decode`, `test_v4_wex4`, `test_qwen38_wex4`, `test_qwen38_mxfp4_experts`, `test_dsv41_wex4`, `test_dsv41_engram_stage`) on the top of the stack under ASan + UBSan with `make test-asan`'s flags and options: all pass, no report; `make check-env`: 863 variables, registry matches. The whole `make -j8 test-c` on the last branch of the series (#2880, which holds this one; run before series 1's two include guards and three comments were reworded, no code differs): every gate passes but `test_uring`, whose "io-wq worker limit" check needs a kernel newer than the WSL2 one here (5.10), as in series 1; it shares no file with this series. Not relied on: colibri's CI (its runs are cancelled by design).
- **Real records** (Windows 10, i7-7700K): a scratch harness, not committed, opens WEX4 files with `wex4.h`, registers their WNM2 blobs with `coli_wex4_register_model` and decodes every expert record with `coli_wex_decode_record`, then compares it with the same expert of a RAW container of the same checkpoint (after canonical zero for value-exact records). Small WEX4 files cut from real checkpoints: DeepSeek V4.1 Flash, 8 experts, WNR3 (88.0% of RAW) and WNR3-CZ (85.2%): **8 of 8 equal** each; Qwen3-235B, 8 experts (89.2%): 8 of 8; MiniMax-M2.1, 8 experts (88.6%): 8 of 8. Decode time per 18.8 MB V4.1 record: 761 ms on one thread; 977 ms each with 8 at once. The whole published V4.1 container goes through this code in the DeepSeek V4.1 PR of this series.
- Not run: macOS, ARM; a GPU (nothing here touches one).

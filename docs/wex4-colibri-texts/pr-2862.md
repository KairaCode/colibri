## 1. What this adds

`c/wex4.h`, a reader for the WEX4 expert container that validates the file's header page and index in place, and `tools/wex4_verify`, a command that checks every record of a WEX4 file against the index's SHA-256 and prints the file's root. `tests/test_wex4_verify.c` runs the tool's code in `make test-c`. No engine includes `wex4.h` yet.

## 2. Why

WEX4 is the container form the engine hooks of the next PRs open. What it adds over the older WEX1-WEX3 form (#2861) is integrity: the first page holds the SHA-256 of the index, the index the SHA-256 of every record, and the hash of the first page, the *root*, names every byte of the file. An engine given a root (`COLI_WEX_ROOT`, next PRs) refuses any other file, and `wex4_verify` is how a user gets that root for a file they trust, or checks a copy on another drive. On the production files of a downstream fork, `wex4_verify` hashed a 64 GB Qwen3.8 container in 7.0 and 10.7 s on two NVMe drives (8 threads, Windows 11); measured there, not here.

Upgrading a WEX1 file to WEX4 in place moves no record: it appends the index and rewrites the first page. On a 123 GB DeepSeek V4.1 container it appended 6,717,440 bytes.

## 4. How it works

A WEX4 file, as the reader sees it:

```
page 0      header page: counts, index offset and size, SHA-256(index), and at byte 4064 SHA-256(bytes 0..4063) = the root
page 1..    blobs and records, each on a 4096-byte boundary (a record is one expert's slab, or a group of other tensors)
last pages  the index: blob table, record table (offset, stored size, decoded size, codec, owner = layer<<16|expert, SHA-256),
            tensor table (name, dtype, shape, record, offset in it), name order, names, metadata
```

The functions in `wex4.h`, in the order a reader calls them:

1. `wex4_parse_header(page, file_bytes, &h)`: the page's own hash (the root), version, required feature bits, every count and the index's place bounded against the file size. No allocation.
2. Read `wex4_align(h.index_bytes)` bytes at `h.index_offset`.
3. `wex4_open(&h, index, len, &view)`: the index's hash, then every rule of the spec on the index in place: names valid UTF-8 and in strict order, tensors tiling their records, records and blobs tiling the file with no gap or overlap, expert records owning distinct (layer, expert) cells of the grid, sizes consistent with their codec. After it returns 0 every offset and size in the view is in bounds.
4. `wex4_get_record` / `wex4_get_tensor` / `wex4_get_blob`: read one table row; `wex4_find`: a tensor by name.
5. `wex4_expert_entry(&view, r, &entry)`: an expert record as the 72-byte `WexEntry` of #2861, checked to be three scale and three weight tensors back to back. This is what the engine hooks consume, so the code after the open is the same as for a WEX1 record.
6. `wex4_sha256`: a record's stored bytes against `rec.sha` (SHA-NI on x86 when the CPU has it, else portable C).
7. `wex4_decode_record`: RAW (copy, padding must be zero), WBP1 (a byte-plane rANS for non-expert tensors) or WNR3.

`tools/wex4_verify.c` is steps 1-3, then step 6 for every blob and record, on N threads (OpenMP), reading 8 MiB at a time unbuffered (`FILE_FLAG_NO_BUFFERING` on Windows, plain `pread` elsewhere). The bytes: [WEX4-SPEC](https://github.com/KairaCode/Wex-WRN2/blob/main/docs/WEX4-SPEC.md).

## 6. How to use it

```sh
make -C c tools/wex4_verify
c/tools/wex4_verify experts.wex4 [THREADS]     # default 8 threads; opens the file read only
```

Exit 0 and a last line `COLI_WEX_ROOT=<64 hex digits>`: every byte is the one the root names. Exit 1: the listed records or blobs do not match (the root is printed with "NOT verified: do not pin"). Exit 2: the file does not open as WEX4. No environment variable; no engine changes behaviour.

colibri does not write WEX4 files yet; Wex-WRN2's `wex4/wex4_convert.py` does (`pack` from safetensors, `upgrade` of a WEX1 file in place). A writer in colibri's tools is listed as open in #2860.

## 7. Compatibility and risk

- No engine includes the header; existing model files and code paths are unchanged.
- Platforms: C99 plus OpenMP pragmas (ignored without OpenMP, like the rest of `c/`). The SHA-NI path is compiled only for x86 GCC/Clang with a runtime CPU check; ARM and other compilers use the portable SHA-256. The tool's I/O is Win32 on Windows and POSIX elsewhere.
- A bad file: `wex4_parse_header` and `wex4_open` return a negative `WEX4_E_*` code and nothing is used; a truncated copy fails the header's file-size check. The tool never writes the file.

## 8. How to test

```sh
cd c
make tests/test_wex4_verify && ./tests/test_wex4_verify
```

Passing ends with:

```
test_wex4_verify: intact file passes with the fixture's root; changed record, padding and blob bytes fail; damaged index / header, truncated and WEX1 files do not open; a resealed wrong record hash fails (1 and 4 threads)
```

The lines before it are the tool's own output for the damaged cases ("FAILED: 1 of 8 ...", "not a valid WEX4 header page ...") and are expected.

## 9. What I ran

- Windows 10, Intel i7-7700K (AVX2, no SHA extensions), MSYS2 UCRT64 gcc 16.2, GNU make 4.4.1: `make tests/test_wex4_verify tools/wex4_verify`, 0 warnings; the test passes; clang 23 with `-fsanitize=undefined,bounds -fsanitize-trap=all`: passes; a build without OpenMP: passes.
- Linux, Ubuntu 26.04 under WSL2, gcc 15.2: the same targets, 0 warnings, the test passes, also with ASan + UBSan.
- **Conformance vectors**: Wex-WRN2's `wex4/vectors/` (112 files: 7 valid, 104 invalid, 1 legacy WEX3) through a small harness, not committed, that calls `wex4_parse_header`, `wex4_open`, the blob hashes and `wex4_decode_record` with hash check on every record: **112 of 112 verdicts agree with the manifest** and every valid file gives the manifest's root; 103 of 104 rejections report the manifest's error class (the other is rejected one step later, as `WEX4_E_DATA` at decode instead of `WEX4_E_BLOB`, because the harness opens the WNM2 model blob itself). Same result on Windows (gcc) and on Linux under ASan + UBSan.
- **Real expert records**: `tools/wex4_verify` on WEX4 files holding real routed experts, a few layers each, written with Wex-WRN2's tools: DeepSeek V4.1 Flash (8 RAW records, 150 MB; 8 WNR3 records, 132 MB), MiniMax-M2.1 (RAW 60 MB, WNR3 53 MB) and Qwen3-235B (RAW 80 MB, WNR3 72 MB): all exit 0 and print their root; the WEX1 form of the DeepSeek file exits 2.
- Linux, the whole `make -j8 test-c` on this branch: every gate passes but `test_uring`, whose "io-wq worker limit" check needs a kernel newer than the WSL2 one here (5.10); it shares no file with this series.
- Not run: `make check`, macOS, ARM. The SHA-NI path of `wex4_sha256` did not run here (the i7-7700K has no SHA extensions); the GitHub-hosted x86 runners have them, so CI's runs of the test go through it.

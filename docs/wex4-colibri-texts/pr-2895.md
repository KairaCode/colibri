# #2895: glm53: AMD MXFP4 checkpoint as published (amd/GLM-5.3-Flash-Quark-MXFP4), experts as fmt 7

Pull request https://github.com/JustVugg/colibri/pull/2895 (closed 2026-11-17, folded into the branch `kaira/wex4-colibri` of this fork). Head was `kaira/glm53-mxfp4 @ 4003d629`. Below: its description as written.

Part of #2860

## 1. What it adds

glm53 runs AMD's MXFP4 checkpoint of GLM-5.3-Flash, `amd/GLM-5.3-Flash-Quark-MXFP4` (revision `b5688f25`, MIT, 62 shards, 185.08 GB), as it is published, with no conversion. Until now glm53 read only its own int4 gs64 container (`tools/convert_glm53.py`) or a GGUF.

- Routed experts that have a `weight_scale` beside them (U8 e2m1 codes `[rows][cols/2]`, U8 ue8m0 exponents `[rows][cols/32]`) stream like the int4 container's experts, as a new matrix format, fmt 7 (`G53_MX`), computed by quant.h's existing `matmul_mxfp4` on the file's bytes.
- The Vulkan and CUDA expert tiers get them as `VKT_SRC_MXFP4_E8M0`, gs 32, the source kind that kimi_k3, mimo and deepseek_v41 already use.
- The shared experts, which are MXFP4 in this checkpoint too, are decoded at load and held at `GLM53_BITS`, like every other dense matrix.

## 2. Why

It is the base the WEX4 container (the next PR) needs: the container is made from this checkpoint, and glm53 can only compare "shards vs container" if it can read the shards.

Running the checkpoint as published replaces the conversion of docs/glm53-flash.md, measured there at "62 shards, 194.7 GB out, 25 hours" on its reference machine, and each routed expert is 13,369,344 bytes to read instead of 14.2 MB for int4 gs64: at 42 sparse layers x 8 experts, 4.49 GB a token instead of 4.77 GB (6% fewer bytes, computed from the shapes, not measured in a run). The experts' values are the checkpoint's own MXFP4 values, with no second quantization.

**No whole-model GLM-5.3 run was done for this PR.** The only machine available has the checkpoint on a SATA SSD and 32 GB of RAM, and the owner chose not to run the whole model there; the whole-model test is listed under "Tests wanted" in #2860. What was run is in section 9.

## 4. How it works along an expert's path

1. `model_load_range` looks at the first expert of the first sparse layer (`g53_expert_form`): U8 with a `…gate_proj.weight_scale` beside it means MXFP4 (`m->mx = 1`); U8 without one is the int4 container as before; a ggml type is a GGUF as before.
2. `expert_geometry`: six pieces per expert, codes then ue8m0 bytes for gate, up, down (13,369,344 bytes per expert on the release, 14.2 MB for int4 gs64).
3. `expert_table_init` finds the pieces by the Quark names (`gate_proj.weight`, `gate_proj.weight_scale`, …).
4. `expert_read` is unchanged: it reads the six ranges into the slot (or maps them).
5. `expert_mats` builds three fmt 7 matrices on the slot: `q4` the codes, the new `e8` field the scale bytes.
6. `mv`, `mm`, `mv_rows`, `mm_rows` call `g53_mx` → `matmul_mxfp4`. The GPU paths of those functions take only resident fmt 0/1/4 matrices, so an expert never reaches them; the batched Metal MoE skips MXFP4 experts (CPU loop).
7. With `COLI_VULKAN=1` or `COLI_CUDA=1` the tier is configured with `VKT_SRC_MXFP4_E8M0` and `glm53_slot_src` hands it the codes and scale bytes as they are.

The shared experts take `load_mat`: a U8 tensor with `name_scale` beside it is decoded to f32 and passes through `quantize_loaded`.

## 5. Changes, file by file

- `c/glm53.c`: `Mat.e8`, `G53_MX` and `g53_mx`; the fmt 7 case in `mv`, `mm`, `mv_rows`, `mm_rows`; `GModel.mx`; `g53_expert_form` (also used by the expert worker's open); MXFP4 geometry, piece names and matrices; the MXFP4 shared-expert branch of `load_mat`; `VKT_SRC_MXFP4_E8M0` in `glm53_vk_tier_start`; the Metal MoE block skips MXFP4.
- `c/tests/test_glm53_mxfp4.c` (new) and its `c/Makefile` rule: a synthetic grid written as the Quark checkpoint writes it.
- `docs/glm53-flash.md`, `docs/ENVIRONMENT.md` (`GLM53_BITS` row), `CHANGELOG.md`.

## 6. Environment variables

None new. `GLM53_BITS` also sets the precision of MXFP4 shared experts (32: exactly the MXFP4 values). Nothing changes for the int4 container or a GGUF: the detection needs a `weight_scale` tensor, which neither has.

## 7. Compatibility and risks

- The int4 and GGUF paths are untouched apart from the detection helper; `test_glm53_live_prefix`, `test_glm53_nucleus` and `test_glm53_image_key` pass.
- MXFP4 shared experts are re-quantized at the default `GLM53_BITS=4` (to int4 gs64); this is a load-time precision choice, as for every other dense matrix of glm53. `GLM53_BITS=8` or `32` keeps more.
- The MTP layer (45, FP8 experts in this checkpoint) is not loaded, as before.
- Not run here: the Vulkan and CUDA tiers with MXFP4 experts on the real model (built: `-DCOLI_VULKAN` and `-DCOLI_CUDA -DCOLI_VULKAN` compile without warnings; not linked, no glslc on this machine).

## 8. Test commands

```sh
cd c
make tests/test_glm53_mxfp4 && ./tests/test_glm53_mxfp4
#   ok   the weight_scale beside the first expert: MXFP4, streamed
#   ok   slots of 26,112 bytes: per matrix the codes, then a ue8m0 byte per 32 values
#   ok   every expert read holds its codes and scales as three fmt 7 matrices; mv, mm and mm_rows equal the dequantization
#   ok   an MXFP4 shared expert through load_mat: the MXFP4 values, decoded at load (GLM53_BITS=32)
# test_glm53_mxfp4: ok
make glm53 && ./glm53 --model <amd/GLM-5.3-Flash-Quark-MXFP4> --ids 785,6722,315,9621,374 --greedy 8
```

## 9. What ran where

- Windows 10, i7-7700K, MSYS2 UCRT64 gcc 16.2.0: `make glm53` (no warnings), `tests/test_glm53_mxfp4` ok; the existing `test_glm53_live_prefix`, `test_glm53_nucleus`, `test_glm53_image_key` ok; `tools/check_env_registry.py` ok.
- WSL2 Ubuntu, gcc 15.2.0: `tests/test_glm53_mxfp4` ok (with the next PR's test, also under ASan and UBSan, no report).
- Compiled only (`-fsyntax-only`, no warnings): `glm53.c` with `-DCOLI_VULKAN`, and with `-DCOLI_CUDA -DCOLI_VULKAN`. Not linked: this machine has no `glslc` for the shaders.
- The shards' expert layout was read from the real checkpoint's headers (amd/GLM-5.3-Flash-Quark-MXFP4 at b5688f25): gate/up weight [2048, 2048] U8 and weight_scale [2048, 128] U8, down [4096, 1024] and [4096, 64], shared experts the same with a `weight_scale`, layer 45's experts F8_E4M3.
- **Not run:** glm53 on the whole checkpoint (CPU, Vulkan or CUDA tier). Tokens, speed and memory on the real model are unknown.

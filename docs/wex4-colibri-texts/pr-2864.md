## 1. What this adds

qwen38 can read its MXFP4 routed experts from a WEX4 container, `COLI_WEX_PATH=<file>`, instead of the `experts-mxfp4/` sidecar of #2822/#2825. The container's records are the sidecar's records (the same bytes, one 4096-aligned record per expert, all in one file), so after the attach everything runs through the sidecar's own code. `COLI_WEX_ROOT` pins the file and checks each record's SHA-256 the first time it is used. Unset, nothing changes.

## 2. Why

One file instead of 48 layer files, a root that names every byte, and a per-record hash. The record bytes and the computation are those of #2825, so there is no speed claim for the container itself in this PR. For scale: in a downstream fork of colibri, Qwen3.8-Flash-Next with the same MXFP4 records in a WEX4 container (24,576 records of 2,613,248 bytes, 64.25 GB) runs in production; `wex4_verify` hashed it in 7.0 and 10.7 s on two NVMe drives (Windows 11, 8 threads). That fork's qwen38 engine is not `dev`'s; nothing here was measured on `dev`'s engine with the real model (section 9).

## 3. Where it sits

On its own it lets qwen38 run the MXFP4 experts from a WEX4 file. WNR3 records (series 2 of #2860) are refused with a message.

## 4. How it works

All in `c/qwen38_core.h`:

```
q38_expert_int4_attach            COLI_WEX_PATH unset -> the sidecar code, exactly as on dev
  COLI_WEX_PATH set -> q38_wex4_attach
    Q38_EXPERT_LOWBIT: unset or mxfp4 (any other low-bit format is refused)
    st_open_fd(&x->S, path)        the container becomes the one file of the sidecar's shard set
    page 0 -> wex4_parse_header    (wex4.h, #2862)  grid == layers x experts?  COLI_WEX_ROOT == root?
    index -> wex4_open             every rule of the spec, in place
    every EXPERT record            codec RAW; six tensors: gate, down, up scales then their codes,
                                   shapes [I][H/32], [H][I/32], [I][H/32] and [I][H/2], [H][I/2], [I][H/2],
                                   offsets as q38_mx4_offsets puts them, U8/E8M0 and U8/I8
                                   -> x->fd[layer] = the file, x->off[cell] = the record's offset
    every expert of the loaded layers present
miss                              q38_load_int4_record / q38_x4_read / the batch loader: the sidecar's code,
                                  one read of record_bytes at x->off[cell], or the mapping (COLI_MAP_EXPERTS=1)
  q38_wex_check                   COLI_WEX_VERIFY and first use: SHA-256 of the record (+ its zero padding)
                                  against the index; mismatch -> the engine stops
```

Anything that does not hold stops the engine with the reason, as a sidecar that was asked for does (`Q38_EXPERT_LOWBIT=mxfp4` without `experts-mxfp4/` refuses on `dev` too): the qwen38 store has no second copy of the MXFP4 experts to fall back to. The prefix store's identity (`Q38_PREFIX_DISK`) stamps the container file in place of the sidecar directory, so a checkpoint written with one source is not resumed with the other. The bytes of the file: [WEX4-SPEC](https://github.com/KairaCode/Wex-WRN2/blob/main/docs/WEX4-SPEC.md).

## 6. How to use it

```sh
c/tools/wex4_verify experts-mxfp4.wex4      # once: prints COLI_WEX_ROOT=<root>
COLI_WEX_PATH=experts-mxfp4.wex4 COLI_WEX_ROOT=<root> ./qwen38 <usual arguments>
```

| Variable | Default | Effect |
|---|---|---|
| `COLI_WEX_PATH` | unset | the container, read as the MXFP4 experts (implies `Q38_EXPERT_LOWBIT=mxfp4`). **Unset: qwen38 behaves exactly as on `dev`** |
| `COLI_WEX_ROOT` | unset | 64 hex digits; another root stops the engine; turns `COLI_WEX_VERIFY` on |
| `COLI_WEX_VERIFY` | on with `COLI_WEX_ROOT`, else off | `1` / `0`: each record's SHA-256 at its first use, read or mapped |

At attach it prints `[qwen38] MXFP4 experts from the WEX4 container <file>: records of N bytes, root <root>[ (pinned)]; first-read SHA-256 on|off`. A container is written by Wex-WRN2's `wex4/wex4_convert.py pack --experts raw --names qwen38` from the sidecar's layer files or AMD's Quark shards (a writer in colibri is open in #2860).

## 7. Compatibility and risk

- Without `COLI_WEX_PATH`: `q38_expert_int4_attach` takes its first branch only when the variable is set; `q38_wex_check` returns at its first line (`wex_sha` is NULL); the identity hash is the same as on `dev`. No behaviour change.
- The sidecar, the FP8 snapshot and every other file are untouched; the container is opened read only.
- CUDA and Vulkan expert tiers: unchanged; as for the sidecar (#2825) they keep MXFP4 experts on the CPU, with their line.
- `COLI_MODEL_MIRROR`: not applied to a container (a line says so); the sidecar's mirrors are unchanged.
- A bad file: a WEX1-WEX3 file, a damaged header page or index, a truncated copy, another grid, a missing expert, a record of another layout, WNR3 records, another or a malformed root: refused before any expert is read. A record changed on disk: stops the engine at its first use when the check is on; with the check off it is served as it is, as a changed sidecar file would be.
- Geometry: the container's record needs widths that are multiples of 32 (the release's are: hidden 2560, moe_intermediate 640). The tiny fixture (`qwen38_tiny_mxfp4`, moe_intermediate 8) has no container form, hence the synthetic test below.

## 1. What this adds

qwen38 reads WNR3 (codec 5) records from the WEX4 container `COLI_WEX_PATH` names, as well as the RAW records of #2864: at attach the container's WNM2 model blob is checked against the index and registered, and each WNR3 record is decoded on the CPU by the thread that reads it, then bound by the sidecar's code as a RAW record is. As for RAW records, anything wrong stops the engine with the reason. Unset, nothing changes; a RAW container reads exactly as with #2864.

## 2. Why

So that a Qwen3.8 container can be the smaller, lossless form: on real Qwen3.8-Flash-Next MXFP4 experts (section 9) the WNR3 records of one layer are 0.878 of their RAW size. It is not a speed change and should not be used as one on the CPU: a Qwen3.8 record (2.6 MB) costs about 150 ms of decode on one core of an i7-7700K, against a few ms to read it from an NVMe drive. Wex-WRN2's measurements found WNR3 slowing Qwen3.8 down on its test machine even with the GPU decode, and the published Qwen3.8 container holds RAW records. This PR makes the engine accept the format the other two engines accept, with the same checks; whether to use it is the user's call.

## 4. How it works

All in `c/qwen38_core.h`, on #2864's attach and read:

```
q38_wex4_attach      as in #2864: header page, index, grid, COLI_WEX_ROOT, every expert of the loaded
                     layers a record of the MXFP4 layout (gate, down, up scales, then their codes)
                     WNR3 records: wex4_expert_entry -> x->wex_nr3[cell]; one WNM2 blob for all;
                     all or none value-exact; the blob read -> coli_wex4_register_model (its SHA-256
                     in the index, its id); any failure stops the engine with the reason
miss
  q38_x4_read        a WNR3 cell -> q38_x4_read_nr3; a RAW cell: as in #2864
  q38_x4_read_nr3    the stored bytes read at the end of the decoded page (wex_record_read_offset)
                     q38_wex_check (COLI_WEX_VERIFY, first use): SHA-256 of the stored bytes
                     wex_nr3_owner_ok: this (layer, expert), the container's canonical-zero form
                     coli_wex_decode_record: decoded in place, then the record copied to the caller's buffer
                     a record that names another expert or does not decode: the engine stops
  q38_load_int4_record  COLI_MAP_EXPERTS=1: a WNR3 record is read and decoded, never mapped
```

Everything after the read (the binding of the three MXFP4 matrices, the CPU kernels, the batch loader, the Vulkan tier's read) is the sidecar's code, unchanged: it sees the decoded record. `q38_wex_check` now takes the length it hashes (a RAW record's decoded bytes plus their padding, a WNR3 record's stored bytes), so both are checked against the index's SHA-256 of what is on disk.

## 6. How to use it

```sh
c/tools/wex4_verify q38_experts.nr3.wex4        # once: prints COLI_WEX_ROOT=<root>
COLI_WEX_PATH=q38_experts.nr3.wex4 COLI_WEX_ROOT=<root> ./qwen38 <usual arguments>
```

No new variable; `COLI_WEX_PATH`, `COLI_WEX_ROOT`, `COLI_WEX_VERIFY` keep #2864's defaults and meanings. **Unset `COLI_WEX_PATH`: qwen38 behaves exactly as on `dev`.** At attach the line gains `(N WNR3, model <id>[, value-exact])` after the record size.

## 7. Compatibility and risk

- Without `COLI_WEX_PATH`, or with a RAW container: no behaviour change (`q38_wex_nr3` is NULL for every cell, the read and the mapped path are #2864's).
- A bad file: a model blob that does not match the index, WNR3 records of two models or mixed value-exact: refused at attach (exit 1). A WNR3 record changed on disk: its stream checks stop the engine at its first read with the hash off, its SHA-256 with it on; a whole record under another expert's name: its owner check stops the engine. There is no fallback, as for RAW records: the qwen38 store has no second copy of the MXFP4 experts.
- Cost: the decode's CPU time on the loading thread, and two buffers of one record (2.6 MB) while it runs. `COLI_MAP_EXPERTS=1` maps RAW records and decodes WNR3 ones into the slot's slab.
- The prefix store's identity (#2864) stamps the container file, so a checkpoint written with the RAW container is not resumed with the WNR3 one.

- Linux, Ubuntu 26.04 under WSL2, gcc 15.2: this branch on its own: `make tests/test_qwen38_wex4 tests/test_qwen38_mxfp4_experts tests/test_v4_wex4`, all pass; then all eight WEX tests of the series (`test_wex_format`, `test_wex4_verify`, `test_wex_decode`, `test_v4_wex4`, `test_qwen38_wex4`, `test_qwen38_mxfp4_experts`, `test_dsv41_wex4`, `test_dsv41_engram_stage`) on the top of the stack under ASan + UBSan with `make test-asan`'s flags and options: all pass, no report; `make check-env`: 863 variables, registry matches. The whole `make -j8 test-c` on the last branch of the series (#2880, which holds this one; run before series 1's two include guards and three comments were reworded, no code differs): every gate passes but `test_uring`, whose "io-wq worker limit" check needs a kernel newer than the WSL2 one here (5.10), as in series 1; it shares no file with this series. Not relied on: colibri's CI (its runs are cancelled by design).
- **Real Qwen3.8 records** (Windows 10, i7-7700K): a scratch harness, not committed, takes the 512 RAW records of layer 7 of the published Qwen3.8-Flash-Next container ([Kaira666/Kaira-WEX4-Experts](https://huggingface.co/Kaira666/Kaira-WEX4-Experts), `qwen38-mxfp4/`, verified against its root), writes them as a WEX4 file with this series' test fixtures, codes them as WNR3 with a WNM2 model trained on all 512 (`tests/wnr3_fixture.h`, the reference encoder), and attaches the result with `q38_expert_int4_attach` (the release geometry, that layer loaded, the root pinned) and loads every expert through `q38_load_int4_record`. The 512 records (2,611,200 bytes each) code to a 1,175,224,320-byte container against 1,337,982,976 bytes of RAW records (0.878) in 77.4 s on one thread; the container attaches (512 WNR3, model `62e9605f`), and **512 of 512 experts load byte-identical to their RAW records**, every record's SHA-256 checked at its first read: 77.9 s on one thread, 152 ms an expert.
- Not run: the qwen38 engine on the real checkpoint (its FP8 trunk is not on this machine), so no token comparison; macOS; CUDA and Vulkan builds (no code of theirs changed).

## 1. What this adds

DeepSeek V4's expert store reads WNR3 (codec 5) records from the WEX4 container `COLI_WEX_PATH` names, as well as the RAW records of #2863: the container's WNM2 model blob is checked against the index and registered when the store opens, and each WNR3 record is decoded on the CPU into the slot's slab, on the thread that missed it. A record that fails is served from the safetensors for the rest of the run, as a RAW record that fails its hash is. Unset, nothing changes; a RAW container reads exactly as with #2863.

## 2. Why

A WNR3 container is the same experts in fewer bytes: the published DeepSeek V4.1 Flash REAP-192 container is 0.854 of its RAW size (123.3 against 144.4 GB), every value the same. #2863 refuses such a file. On the CPU the trade is disk bytes for CPU time: here the reference decoder takes 761 ms for an 18.8 MB V4.1 expert on one thread of an i7-7700K (24.7 MB/s; #2876), so a WNR3 container on the CPU pays only where the drive is slower than the decode, or when disk space is what is short; the GPU decode (series 3) is where it pays for speed.

Measured with this PR's store on real data (section 9): the 192 experts of layer 0 of DeepSeek V4.1 Flash REAP-192 (the V4 store reads that checkpoint's expert tensors) from the published WNR3 container, against the same experts from the safetensors: **192 of 192 experts the same values** as the shards' (every scale byte equal; the container is value-exact, so the shards' 398,490,631 FP4 codes -0 are +0 in it and every other code byte is equal), 192 decoded, 0 refused. One thread, one expert at a time: 10.7 s from the shards, 217.5 s from the container (1.13 s an expert: 16 MB read, SHA-256, 761 ms decode).

## 4. How it works

All in `c/deepseek_v4.c`, the `v4_wex_*` functions of #2863:

```
coli_deepseek_v4_expert_store_open
  v4_wex_open        as in #2863: header page, index (wex4.h), grid, COLI_WEX_ROOT
                     every EXPERT record: wex4_expert_entry (wex4_open admits RAW and WNR3 only)
                     WNR3 records: one WNM2 blob for all of them; all or none value-exact
                     the blob read -> coli_wex4_register_model: its SHA-256 in the index, its id
                     value-exact -> coli_wex_container_refused (DSV4_CUDA_MOE_MASKED=1 refuses)
                     any failure: a [v4_wex] line, and the safetensors serve every expert
  v4_wex_bind        as in #2863: every record has its expert's shapes and sizes
miss (lookup_hot / v4_read_expert_record -> v4_wex_read)
  RAW                as in #2863
  v4_wex_read_nr3    WNR3: the stored bytes read at the end of the record's decoded page
                     (wex_record_read_offset; O_DIRECT into the hot store's aligned slab)
                     COLI_WEX_VERIFY, first read: SHA-256 of the stored bytes against the index
                     wex_nr3_owner_ok: the record says it is this (layer, expert), CZ as the container
                     coli_wex_decode_record: decoded in place, the slab starts with the RAW bytes
                     (an unaligned slab: decoded in a scratch page and copied)
                     any failure -> v4_wex_refuse: this expert from the safetensors for the run
prefetch             the advice covers the record's stored bytes, as for RAW
destroy              [v4_wex] reads=N (WNR3 decoded M) bytes=... fallbacks=... refused=...
```

The decode runs on the thread that missed, inside the store's existing read path; nothing else in the engine knows a record was coded. The hot store's slab is `record_bytes + COLI_V4_EXPERT_SLAB_SLACK` (16 KiB), which holds the decoded page, so the record is read into the slab and decoded there (the decoder takes one scratch buffer of the decoded size while it runs). A record whose bytes say they are another expert's (a damaged index, records swapped between files) is refused even when its SHA-256 is right.

## 6. How to use it

```sh
c/tools/wex4_verify v4_flash_experts.nr3.wex        # once: prints COLI_WEX_ROOT=<root>
COLI_WEX_PATH=v4_flash_experts.nr3.wex COLI_WEX_ROOT=<root> ./deepseek_v4 <usual arguments>
```

No new variable. `COLI_WEX_PATH`, `COLI_WEX_ROOT` and `COLI_WEX_VERIFY` keep #2863's defaults and meanings (path unset; no root; the hash on when a root is pinned). **Unset `COLI_WEX_PATH`: the store reads the shards exactly as on `dev`** (`v4_wex_open` returns NULL at its first line, nothing else runs). A RAW container: `v4_wex_read` takes the RAW branch of #2863 unchanged.

At open: `[v4_wex] WEX4 container <file>: N of M experts (K WNR3, model <id>[, value-exact]), root <root>[ (pinned)]; first-read SHA-256 on|off`.

## 7. Compatibility and risk

- Without `COLI_WEX_PATH`, or with a RAW container: no behaviour change. The only change on the RAW path is that a failed hash's message goes through `v4_wex_refuse` (same words).
- A bad file never reaches a kernel: a model blob that does not match its SHA-256 in the index, WNR3 records of two models, mixed value-exact and not: the container is not used, with a line. A WNR3 record changed on disk: its rANS stream checks refuse it at its first decode with the hash off, its SHA-256 with it on; a whole record under another expert's name: its owner check refuses it; each time that expert comes from the safetensors for the rest of the run. The test covers each case.
- Value-exact (canonical-zero) containers decode -0 as +0: the same values. Under `DSV4_CUDA_MOE_MASKED=1` such a container is not used, as in Wex-WRN2.
- Cost: CPU time on the missing thread (761 ms per 18.8 MB V4.1-size expert on an i7-7700K core), and the decoder's scratch buffer (one decoded record) per decode in flight.
- GPU tiers: they consume the host slab, which holds the decoded bytes; no CUDA, HIP or Vulkan code changed.

**Decision** (taken for this series, recorded here): with `DSV4_CUDA_MOE_MASKED=1`, DeepSeek V4 refuses a canonical-zero (value-exact) container, on purpose: the masked DeepGEMM MoE path is not deterministic and emits -0 itself, so "-0 stored as +0 gives the same output" is not proven there. The engine then reads the safetensors, with the `[v4_wex] value-exact (canonical-zero) container refused` line. A plain (not canonical-zero) WNR3 container is used under it as under any other path.
